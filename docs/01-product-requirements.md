# 제품 요구사항과 초기 범위

갱신일: 2026-10-09. 최신 제품 방향은 workspace·채팅을 중심으로 한 **AI 직접 문서 편집**이다. 상세 구현 작업은 [MVP 작업 계획](11-workspace-agent-mvp-plan.md)을 따른다. 이번에는 작업 문서만 갱신했으며 현재 실행판에 MVP 기능을 구현한 상태는 아니다.

## 제품 목적과 사용 환경

Jueony는 공무원이 업무별 자료와 대화를 관리하고 AI와 함께 한글 문서를 작성·편집하는 Windows 프로그램이다. 가운데 채팅에서 지시하면 AI가 오른쪽의 실제 HWP/HWPX 문서를 편집한다. 사용자는 같은 문서를 계속 직접 편집할 수 있다.

AI의 최종 작업 범위는 전체 문서의 내용·구조·서식·표·개체·쪽 설정·저장이다. 초기 MVP는 검증 가능한 본문 명령부터 연결한다. 특정 문단을 선택하고 매번 승인하는 흐름을 제품의 중심으로 두지 않는다. 변경 확인과 되돌리기는 직접 편집을 지원한다.

편집·업무 자료 연결·대화 기록은 로컬에서 동작한다. AI 호출은 설정된 허용 서버와 연결될 때 수행한다. 인터넷 단절과 기관 내부 AI 서버 단절은 구분하며, 모델 연결이 끊겨도 기존 문서 편집·저장은 가능해야 한다. 실행에 필요한 Studio·WASM·글꼴은 로컬 묶음에 포함한다.

한글 2024를 사용 흐름의 기준으로 삼되 100% 호환성을 주장하지 않는다. 현재 실제 실행은 Rust 런처와 설치된 Edge/Chrome을 사용하며, Tauri 소스와 검증된 실행 경로를 구분한다.

## 대표 사용자 흐름

1. 업무 하나를 workspace 하나로 만들거나 기존 workspace를 선택한다.
2. 기존 로컬 폴더를 여러 개 연결하고 하위 계층을 탐색한다.
3. workspace 안에서 채팅을 생성·전환·이름 변경한다.
4. 트리에서 HWP/HWPX를 열거나 새 문서를 만들고 오른쪽 편집기에서 확인한다.
5. 연결한 LLM 제공자와 모델을 선택한다. 필요하면 파일 또는 폴더를 이번 요청의 참고 자료로 지정한다.
6. 자연어로 요청한다. 앱은 현재 채팅·미저장 최신 문서·지정 자료로 문맥을 구성한다.
7. LLM이 구조화된 명령을 반환하면 앱이 대상·인자·지원 여부·문서 버전을 검증하고 실제 문서에 직접 적용한다.
8. 사용자는 결과와 사용 자료를 확인하고 직접 편집하거나 후속 요청한다.
9. 필요하면 변경을 되돌리거나 기존 저장 기능으로 파일에 저장한다.
10. 앱을 다시 열면 workspace·폴더 연결·채팅·최근 작업 상태를 복원한다. 원본 파일 접근 권한은 필요할 때 다시 확인한다.

## 자료와 문서의 소유권

Workspace가 폴더 연결과 채팅·작업 문서를 소유한다. 같은 workspace의 채팅은 폴더를 공유하지만 대화와 실행 기록은 독립적이다. 연결된 폴더 전체가 매 요청에 자동 전송되는 것은 아니다.

참고 파일/폴더 선택은 요청 시작 시 확정한다. 선택 폴더의 하위 지원 파일도 명시적인 목록과 범위로 기록한다. 현재 문서는 실제 editor snapshot을 사용하며 디스크의 옛 내용을 기준으로 편집하지 않는다. 같은 파일의 중복 감지를 이유로 업무 경계를 합치지 않는다.

첫 참고 형식은 HWP/HWPX·UTF-8 TXT/Markdown을 목표로 한다. PDF·DOCX·표 계산 파일·이미지 OCR은 검증 전 지원으로 표시하지 않는다. 파일 수/크기/문맥 한도를 넘으면 명확히 안내한다. 문서 내 지시나 자료 텍스트는 시스템 명령이나 권한이 아니다.

폴더 연결 해제는 앱의 연결 정보만 제거한다. 기존 사용자 파일을 삭제하거나 이동하지 않는다. 업무 메타데이터·대화·복구 기록의 보관과 원본 파일의 보관을 구분한다.

## LLM과 Agent의 경계

의존성은 `UI → Application/Agent → LLM Port ← Provider Adapter`다. 제공자 SDK와 응답 형식은 adapter에 한정한다. provider 선택과 모델 ID 선택을 분리하고 실제 등록한 연결만 노출한다.

Agent는 한 번의 문맥 구성·호출·검증·도구 실행·기록을 수행한다. 자동 RAG, 벡터 DB, 반복 계획/실행, 자기평가·자동 재시도는 MVP에 넣지 않는다. RAG는 나중에 Context 공급 경계에, loop는 실행 제어에 추가한다.

실제 provider·endpoint·모델·인증정보는 미확정이다. mock은 검사용이며 실제 호출 완료 기준을 대신하지 않는다. API 키를 채팅/일반 로그/업무 DB에 보관하지 않는다.

## 후속 범위와 이전 계획의 관계

공통 자료/업무 자료/일회성 첨부의 세분화, 폴더 없이 드래그·붙여넣기 첨부, 자동 검색과 출처 검색 고도화, 기관 HyperCLOVA X 고유 adapter, 세부 보관 정책은 후속 요구사항으로 유지한다. 지금 MVP는 연결 폴더와 명시 자료, 실제 provider 하나로 범위를 좁힌다.

단일 문단 mock → 비교 → 승인 → 적용 과제는 초기 기술 검증 계획이었다. 여러 위치의 직접 편집을 목표로 하는 현재 MVP의 최종 범위나 필수 승인 흐름으로 적용하지 않는다. 표·서식은 기존 엔진에서 검증된 작은 명령부터 추가하고 개체/고급 쪽 설정은 후속 capability로 확장한다.

[기본 편집기 보강](10-basic-editor-work-plan.md)의 필요한 부분을 재사용한다. 모든 기본 편집기 개선 완료를 기다리지 않고 [MVP 작업 순서](11-workspace-agent-mvp-plan.md)를 따른다. [문서 호환성 검증](04-compatibility-validation.md)은 독립 한글 판정을 위한 관문으로 계속 유지한다.

## 완료 판단과 미정 사항

최소 완료는 업무/폴더/독립 채팅/재시작 복원과 실제 모델에 의한 문서 변경·수동 후속 편집·되돌리기·저장이 함께 작동하는 것이다. 메시지에만 초안이 생성되거나 mock으로만 동작하면 완료가 아니다.

필요한 미정 정보는 실제 provider/endpoint/인증, 기관망 허용 범위, 대표 문서와 한글 빌드/글꼴, 지원 문서 규모다. 미정 부분과 검증하지 못한 부분은 결과에서 별도 표시한다. 무수정 저장 손상·업무 격리 실패·후속 사용자 편집 유실은 우선 해결할 결함이다.
