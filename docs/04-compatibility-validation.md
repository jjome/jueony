# 문서 호환성 검증 계획

호환성은 열기, 화면 표시, 무수정 저장, 편집 저장, 되돌림 저장, 실제 한글 재열기를 각각 판정한다. 파싱 성공이나 editor 계약 테스트만으로 한글 호환을 주장하지 않는다. 첫 검증의 최종 기준은 동일 원본에 같은 수정을 수행한 실제 한글 결과와 내용·서식·배치를 대조하는 것이다.

## 현재 개발판의 복잡한 문서 수동 검수

2026-10-09 사용자가 한글에서 저장 파일 재열기와 한글 입력에 성공했다고 보고했다. [사용자 확인 기록](evidence/user-validation-2026-10-09.json)은 시험 문서·형식·한글 빌드가 제공되지 않은 `USER_REPORTED_PASS`다. 아래 세부 항목이나 두 형식 전체가 통과했다는 의미는 아니다.

현재 AI 흐름은 미구현이므로, 다음 수동 편집 시험부터 진행한다. 후술하는 V04~V11 등의 AI 관문과 구분한다.

1. 가장 자주 쓰는 공문, 표 중심 문서, 여러 쪽 보고서 등 대표 사본 3개로 시작한다. 원본은 별도 보존한다. 처음에는 같은 형식으로 저장하고, HWP↔HWPX 변환은 별도 시험으로 둔다.
2. 원본을 실제 한글에서 열고 쪽수와 주요 요소를 기록한 뒤 PDF 기준본을 만든다. 한글 버전·글꼴·용지·여백·인쇄 설정을 고정한다.
3. 원본을 Jueony에서 열어 화면을 비교한다. 아무것도 수정하지 않고 다른 이름으로 저장한 뒤 한글에서 처음 재열어 내용·배치·경고를 확인한다. 경고 후 한글이 복구·재저장한 파일로 최초 결과를 대체하지 않는다.
4. 다시 원본을 열고 본문 한 문장 또는 표 한 셀만 수정하여 별도 저장한다. 한글에서도 원본에 정확히 같은 수정을 한 기대본을 만들어 비교한다. 추가 글자로 인해 정상적으로 달라지는 줄바꿈과 손상을 구분한다.
5. 다시 원본에서 같은 편집을 한 뒤 즉시 되돌리고 별도 저장한다. 실제 한글에서 원본과 내용·서식·배치가 복원됐는지 본다.
6. 각 결과를 동일한 한글과 인쇄 설정으로 PDF 출력해 전체 페이지를 비교한다. PDF 모양 외에도 한글에서 표 셀, 그림 개체, 필드 등이 원래 구조와 동작을 유지하는지 확인한다.

| 유형 | 특히 볼 항목 |
| --- | --- |
| 공문·결재 양식 | 결재란·병합 셀·직인/대체 그림·문단 간격·문서 끝 누락 |
| 긴 표 | 행·열·셀 텍스트, 병합·분할, 열 너비, 행 높이, 테두리, 쪽을 넘는 표와 반복 제목 |
| 여러 쪽 보고서 | 전체 쪽수, 쪽번호, 머리말·꼬리말, 목록 번호, 구역·쪽 나눔, 빈 쪽 |
| 그림·글상자 | 위치·크기·자르기, 본문과의 배치, 겹침 순서, 캡션 |
| 특수 요소 | 각주·미주, 다단, 수식, 차트, 책갈피·링크·누름틀/필드의 내용과 동작 |

앱 화면만 다르고 저장본을 한글에서 열면 정상인 경우는 표시·조판 문제로, 저장본도 달라지면 저장·개체 보존 문제로 각각 기록한다. 앱에서 보기에 정상이어도 저장 후 누락되면 저장 실패다. 파일 열기 성공만으로 합격 처리하지 않는다.

무수정 저장과 되돌림 저장은 설명되지 않는 내용·쪽수·줄바꿈·개체 변화가 없어야 한다. 편집 저장은 한글 수동 기대본과 비교한다. 내용 누락·숫자 변경·셀 이동·개체 유실·복구 경고는 해당 문서군의 지원을 막는 실패로 분류한다. PDF의 픽셀 점수나 파일 해시 하나로 전체 호환성을 판정하지 않는다.

간단한 기록 예: `문서ID / 입력·출력 형식 / 저장 경로(무수정·수정·되돌림) / 한글 빌드 / 원본·결과 쪽수 / 문제 쪽·개체 / 기대·실제 / PASS·FAIL`. 실패 사례는 원본 사본·Jueony 출력·한글 기대본·비교 화면을 같은 폴더에 보관한다. 기관 자료는 승인된 로컬 환경에서 비식별 사본으로 시험한다.

## 검증 환경 고정

실행 전에 Windows 제품·빌드·아키텍처, WebView2 버전, 앱과 Studio·WASM 해시, rhwp commit, 한글 제품명·빌드, 설치 글꼴 이름·버전·해시, DPI·배율·용지·인쇄 설정을 기록한다. 기준 제품은 한글 2024이며, 실제 검수한 세부 빌드는 결과마다 별도로 기록한다.

검수 corpus는 공개 가능한 합성 문서와 기관에서 사용을 허가한 비식별 문서로 시작한다. 샘플이 공개 저장소에 있다는 사실만으로 우리 제품의 재배포 자산으로 사용하지 않는다. 기관 원문은 공개 이슈·외부 변환 서비스에 올리지 않는다.

## 첫 corpus

최소 4개 유형을 실제 한글에서 HWP와 HWPX로 각각 저장하여 8개 입력을 준비하는 것을 목표로 한다. 초기 합성 fixture는 개발용이며, 실제 한글의 독립 출력과 연결되기 전에는 최종 합격 자료가 아니다.

| 유형 | 포함할 요소 | 검증 목적 |
| --- | --- | --- |
| C01 본문 기본 | 제목, 앞·대상·뒤 문단, 동일 글자 서식, 짧은 한글·숫자·날짜 | 본문 1문단 수정·되돌림·같은 형식 저장 |
| C02 페이지 경계 | 여러 쪽, 쪽 끝에 가까운 본문, 머리말·꼬리말·쪽번호 | 줄바꿈·쪽수 변화와 `PAGE_COUNT_CHANGED` 복구 |
| C03 공문 주변 개체 | 본문 대상 외에 표·결재란·이미지·직인 대체 도형 | 대상 문단 외 요소가 편집·저장에서 보존되는지 |
| C04 거절 대상 | 혼합 글자 서식, 필드·컨트롤, 표 내부, 긴 문단 | 지원하지 않는 AI 명령이 명시적으로 거부되는지 |

한글에서 C01의 수정 대상 문단을 수동으로 바꾼 기대본도 만든다. mock 제안과 수동 변경의 문자열은 정확히 같아야 한다. 데이터와 이름은 모두 합성값을 사용한다.

후속 corpus에는 중첩·병합 표, 반복 머리행, 각주·미주, 다단, 글상자, 누름틀, 책갈피, 수식, 차트, 번호·글머리, 구역 나눔, 옛한글·PUA·보조 평면 문자, 링크, 암호·배포용·손상 문서를 포함한다. 암호·서명·전자결재 관련 문서는 별도 정책·호환성 확인 전 편집 지원 대상으로 약속하지 않는다.

## 저장 경로별 시험

| 경로 | 첫 검증 | 확인할 결과 |
| --- | --- | --- |
| HWP 열기 → 변경 없이 HWP 저장 | 필수 | 무수정 재직렬화로 생기는 누락·경고·서식 손상 |
| HWPX 열기 → 변경 없이 HWPX 저장 | 필수 | XML·리소스·표·서식의 보존 |
| HWP 한 문단 수정 → HWP 저장 | 필수 | 승인한 문자열만 변경, 실제 한글 재열기 |
| HWPX 한 문단 수정 → HWPX 저장 | 필수 | 동일 기준 |
| 각각 적용 → 즉시 되돌리기 → 같은 형식 저장 | 필수 | 원문·서식·주변 개체 복원 |
| HWP → HWPX, HWPX → HWP | 후속 독립 시험 | 포맷 변환 손실을 일반 저장과 별도로 분류 |
| 원본 경로 덮어쓰기 | 파일 서비스 관문 | 외부 변경·잠김·실패·중단 시 기존 파일 보호 |

저장 결과를 다시 engine으로 여는 검사는 추가한다. 이것은 engine 자신의 입출력 일관성 검사이며 실제 한글 검사와 별도로 결과를 남긴다.

## 실제 한글 검수 절차

1. 검수자는 입력 원본, 무수정 저장본, 적용 저장본, 되돌림 저장본의 해시와 파일명을 대조한다. 이름이 비슷한 다른 run의 결과를 검사하지 않는다.
2. 지정 한글 버전에서 네 파일을 연다. 오류·복구·호환성 경고가 있으면 메시지와 해당 파일을 기록한다. 경고를 무시하고 다시 저장해서 첫 실패를 숨기지 않는다.
3. 적용본의 목표 문단을 기대 문자열과 대조한다. 원본에는 그 변경이 없어야 하고 되돌림본에는 원문이 있어야 한다.
4. 글꼴·크기·굵기·문단 간격·들여쓰기·정렬·쪽수·줄바꿈과 주변 표·이미지·결재란을 확인한다. 한글이 자동 대체한 글꼴도 기록한다.
5. 원본·수동 기대본·앱 결과를 같은 인쇄 설정으로 PDF 출력한다. 화면 캡처와 PDF는 문서의 같은 페이지·영역으로 맞춘다.
6. 전체 쪽수와 내용 순서·누락·중복을 검사하고 영향을 받은 쪽을 직접 비교한다. 텍스트 추출·해시·픽셀 점수 하나로 시각 품질을 대신하지 않는다.
7. 필요하면 앱 저장본을 한글에서 별도 이름으로 다시 저장하고 재열어 본다. 이 결과는 앱의 첫 저장본과 다른 산출물로 보관한다.

원본 파일의 무결성 확인에는 SHA-256을 사용한다. 재직렬화된 HWP/HWPX가 원본과 byte-identical해야 한다고 요구하지는 않는다. 의미·서식·리소스·배치의 보존이 합격 조건이며 정상적인 메타데이터·압축 차이는 따로 설명한다.

## 전달할 증거 묶음

첫 구현을 완료할 때 아래 구조를 생성한다. 현재는 체크리스트와 [결과 기록 양식](validation-results.csv)만 준비되어 있으며, 실제 편집 산출물은 아직 없다.

```text
validation/<run-id>/
  environment.json             앱·engine·OS·한글·글꼴·네트워크 조건
  manifest.json                fixture별 해시·원문·기대문·target·저장 경로
  inputs/                      수정하지 않은 HWP·HWPX 원본
  expected/                    실제 한글에서 수동 수정한 기대본
  outputs/noop/                무수정 저장본
  outputs/applied/             mock 수정 적용본
  outputs/reverted/            즉시 되돌림 저장본
  receipts/                    context·apply·revert·save 결과
  hancom-pdf/                  원본·기대본·앱 결과 인쇄 PDF
  screenshots/                 동일 페이지·영역 비교
  network/                     외부 요청 검사 결과
  review.csv                   검수자·버전·항목별 판정·결함
```

manifest에는 `fixture_id`, `source_sha256`, sourceFormat, target, beforeText, replacement, 예상 출력 파일, 실제 출력 sha256, engine commit, 실행 시간, 원본 수정 여부를 넣는다. 기관 문서로 확장할 때 receipt·diff·PDF에도 원문이 포함될 수 있으므로 원본과 같은 보관 정책을 적용한다.

## 판정과 다음 단계

판정은 `PASS`, `FAIL`, `NOT_RUN`, `BLOCKED`로 구분한다. 실패에는 재현 증거, 미실행에는 필요한 환경을 적는다. 전체 합격률 평균으로 중요한 실패를 덮지 않는다.

첫 기술 관문은 오프라인 흐름과 V01~V16의 해당 경로 통과다. 별도의 문서 관문은 지정 한글에서 기본 HWP·HWPX의 무수정·적용·되돌림 저장 검수 통과다. 한글 검수가 없으면 기술 데모 완료까지만 말할 수 있다. C03에서 손상이 발견되면 해당 문서군의 편집·저장 지원을 보류하고 engine 문제를 먼저 분리한다.

rhwp 엔진을 직접 수정하게 되면 업스트림의 Native·fresh WASM 시각 검증 규칙도 따른다. 그 규칙의 점수 기준을 제품 전체 호환성 보증으로 바꾸어 사용하지 않는다.
