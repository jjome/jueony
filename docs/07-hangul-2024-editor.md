# 한글 2024 기준 편집기 — 현재 구현과 검수

2026-10-09. 처음 요청된 조사·설계 이후, 사용자가 한글 2024 기준의 편집기 구현과 중간 커밋을 요청했다. 현재 우선순위는 기본 문서 편집기를 먼저 사용하는 것이다. AI·업무 자료 연결은 후속 과제로 유지한다.

## 아침에 실행할 위치

루트 `Start-Jueony.cmd`를 더블클릭한다. 실제 실행 파일은 `build/jueony-preview/JueonyEditor.exe`다. `dist` 폴더를 옆에 둔다. Edge 또는 Chrome 설치가 필요하며 Node.js·Python은 실행에 필요하지 않다. 폴더를 옮길 때는 `jueony-preview` 전체를 함께 복사한다. 설치·배포·자동 시작 등록은 하지 않았다.

| AI/자료 공간 | 설계 문서만 있음 | mock 수정 승인 흐름, 업무별 workspace, HyperCLOVA X 연결은 미구현 |

현재 결과를 한글 2024의 완전한 대체재나 100% 호환 제품으로 취급하지 않는다. 상용 기본 글꼴은 포함하지 않고 rhwp의 공개 글꼴로 대체한다. 문서의 글꼴 이름이 같아도 실제 화면의 글자 폭·줄바꿈은 다를 수 있다.

## 실제 검증 증거

[빌드 기록](evidence/editor-build-2026-10-09.txt), [테스트 로그](evidence/editor-tests-2026-10-09.txt), [런처 검사](evidence/launcher-http-2026-10-09.json), [파일 해시와 검증 상태](evidence/editor-validation-2026-10-09.json)를 함께 보관한다. [표 작성 화면](evidence/editor-table-2026-10-09.jpg)과 [최종 시작 화면](evidence/editor-final-2026-10-09.jpg)도 포함한다.

앱 테스트 `apps/editor/tests`의 8개 검사가 통과했다. 본문 3개 문단의 텍스트와 경계, 3×3 표의 9개 셀, 양쪽 형식 재저장, 저장 후 닫기의 실제 생성 파일, 저장 버전 충돌·외부 파일 변경·쓰기 실패를 검사한다. `fixtures`는 UI에서 만든 합성 문서다. 같은 rhwp 엔진으로 검증했으며 독립된 한글 판정이 아니다.

Rust 런처의 HTTP 통합 검사 13개는 화면·메타데이터·WASM 제공과 MIME/해시, HEAD, 경로 이탈·잘못된 Host·POST 거부를 확인했다. 외부 요청 허용 범위는 CSP로 제한하며 정적 서버에 문서 읽기/쓰기 API는 없다. 운영체제의 인터넷 연결을 끊은 상태에서 앱 전체·브라우저 전체 네트워크를 계측한 검수는 하지 않았다.

UI 시험 중 확인하고 수정한 결함:

1. 다른 이름으로 저장에서 파일 이름을 두 번 묻던 동작을 한 번으로 줄였다.
2. iframe 다운로드가 저장 파일을 만들지 못하던 경로를 부모 창 소유 다운로드로 바꿨다. 저장 확인 전에는 문서와 복구 초안을 유지한다.
3. 표 만들기의 잘못된 명령 ID를 실제 `table:create`에 연결했다. 연결되지 않은 명령을 조용히 감추는 대신 개발 오류로 드러내도록 바꿨다.
4. 새 탭을 열 때 다른 열린 문서의 복구 초안을 다시 제안하지 않도록 분리했다.

내장 검증 브라우저에서는 초기 로드에 출처가 표시되지 않은 `MutationObserver.observe` 오류도 관찰했다. 편집기 오류 수집기에는 같은 스택이 들어오지 않았고 핵심 UI 시험은 수행됐으나 원인을 확정하지 못했다. 외부 Edge/Chrome 및 WebView2에서 다시 확인할 미해결 항목으로 남긴다.

## 한글 2024 검수 순서

1. `fixtures/three-paragraphs.hwp`와 `.hwpx`를 한글 2024에서 연다. 제목, 본문 세 문단, 쪽 수, 깨짐·복구 경고를 기록한다.
2. `fixtures/schedule-table.hwp`와 `.hwpx`를 연다. 3×3 셀, 아래 9개 값, 표 테두리와 줄바꿈을 기록한다.
3. 한글에서 각 파일을 다른 이름으로 저장하고 이 편집기에서 다시 연다. 한글에서 추가한 글자·문단·표의 보존을 확인한다.
4. 실제 업무 문서 사본으로 무수정 저장 → 한글 재열기, 본문 편집 저장 → 한글 재열기를 분리한다. 결재란·도장·글상자·각주·머리말·다단·쪽 나눔을 우선한다.
5. 같은 Windows 배율, 프린터, 한글 빌드, 글꼴으로 PDF와 화면 기준본을 확보한다. 쪽 수·줄바꿈·셀 경계 차이를 기능별로 분류한다.

## 다음 구현 순서

1. **Windows 입력·파일 저장**: 실제 IME 조합, 원본 저장, 저장 취소, 외부 변경, 잠긴 파일, 디스크 오류, 종료 중 미저장 문서. Tauri 빌드가 허용된 개발 환경에서 네이티브 호스트를 검증한다.
2. **편집 기능과 화면 정합성**: 대표 문서와 공식 한글 동작을 기준으로 글자/문단 모양, 표 병합·분할·넘김, 그림·글상자, 용지·쪽 번호·머리말·각주·인쇄를 차례로 비교한다. 버튼 존재만으로 합격 처리하지 않는다.
3. **저장 호환성**: 지원 문서군과 글꼴을 고정하고 한글의 열기·재저장·PDF 비교를 통과시킨다. 엔진 자체 변경은 upstream의 새 WASM·독립 한글 기준본 검증 지침을 따른다.
4. **첫 AI 과제**: 한 본문 문단의 원문/서식/주변 문맥 adapter, mock 제안, diff, 승인, apply/revert, 문서 버전 충돌, 저장 완료 통지를 연결한다. 실패한 위치를 인접 문단에 임의 대응하지 않는다.
5. **업무 공간과 기관 API**: 처음 작성한 01~06 문서를 따른다. 기관 endpoint와 권한·자료 반출 정책을 실제로 확인한 뒤 연결한다.

Rust를 사용한다는 선택만으로 한글과 동일한 조판이나 모든 기능이 보장되지는 않는다. 각 단계의 완료 기준은 동작 시험과 실제 문서 비교 결과다.
