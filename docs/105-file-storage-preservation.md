# 105. 파일 저장·복구·형식 보존 보강

2026-10-16. 파일 영역에서 실제로 재현한 저장 결함과 실패 수명을 우선 보강한다. [기능별 작업표](features/05-files-storage-recovery.md)의 완료 범위를 따르며, 한글 전체 입출력과 미지원 XML 기능까지 완료했다는 뜻은 아니다.

## 저장 경로

열린 문서 → 내보낸 사본의 내용·서식 보존 검사 → 해당 HWP 겹침 표의 배치 재열기 검사 → 원본 파일 충돌 검사 → 임시 쓰기 → close → 실제 저장 파일을 다시 읽어 SHA-256 확인 → 저장 연결·형식 갱신 → 수정 표시 해제.

읽을 수 있는 파일 handle에서는 실제 저장 바이트가 일치하기 전 성공으로 처리하지 않는다. 다운로드 방식은 파일 handle의 재읽기를 할 수 없으므로 기존의 사용자 저장 확인 흐름을 유지한다.

| 항목 | 이번 변경 | 실패할 때 유지하는 상태 |
| --- | --- | --- |
| 저장 결과 확인 | close 성공 뒤 파일 바이트를 다시 읽고 사본과 비교 | 열린 내용·dirty·이전 파일 기준 지문 |
| 쓰기 오류 | open/write/close 전후 실패와 abort 실패를 구분 | 잠금 해제, 편집 내용 유지, 거짓 성공 방지 |
| 다른 이름·형식 저장 | 성공한 연결의 출력 형식을 기억해 다음 Ctrl+S에도 사용 | 취소·실패 시 기존 연결·이름·출력 형식 유지 |
| 새 파일 열기 | 새 문서 파싱 성공 뒤 이전 연결의 형식 기억 해제 | 다른 문서로 과거 저장 형식이 섞이지 않음 |
| 속성창 정밀도 | 표시한 수치와 실제 변경값을 구분해 변경한 속성만 기록 | 141HU→0.5mm 표시 반올림으로 원본이 변하지 않음 |
| HWP 겹침 후속 본문 | 관측한 단일 본문 글줄과 표 호스트 원점을 함께 저장 | 해석하지 못한 원본은 자동 정규화하지 않음 |
| 알려진 배치 손상 | Native HWP5의 인접한 겹침 표에서 전체 공개 개체·텍스트 배치를 저장 전후 비교 | 불일치·미관측 시 원본 파일 쓰기 차단 |
| 복구본 쓰기 실패 | IndexedDB quota와 transaction abort에서 이전 checkpoint 보존 | 원본 파일·열린 편집 내용·기존 유효 복구본 |

close 실패가 실제 commit 이후 발생하거나 파일 바이트가 손상된 경우 디스크가 이미 바뀌었을 수 있다. 이때 원본이 반드시 그대로라고 보고하지 않는다. 저장 실패와 dirty 상태를 유지하고, 이전 지문과 달라진 파일에 대한 후속 덮어쓰기를 거절한다. 실제 OS 공유 잠금·디스크 장애·원자적 교체의 보장은 별도 Windows 검수가 필요하다.

## 보존 검사의 범위

겹침 표 배치 검사는 원본 출처가 확인된 Native HWP5, 같은 구역에서 인접한 본문 표, 뒤 표의 겹침 허용이 관측된 경우에 한정한다. 다른 형식에서 HWP로 변환하는 모든 경우나 문서 전체의 한글 조판 동일성을 주장하지 않는다.

표·셀·본문 글줄의 공개 배치 정보를 생략·투영·원점 재설정하지 않고 비교한다. 기존 0.2 오차 기준을 유지하고 페이지·노드·자료량 한도를 넘기거나 배치를 읽지 못하면 저장하지 않는다. 임시 portable 글꼴 측정 선택은 성공·실패와 관계없이 원래 화면 환경으로 복원한다. 지원되지 않는 겹침 원본에서는 새 자동 복구본 생성도 보존 검사에서 거절될 수 있으며, 기존 복구본은 유지한다.

같은 저장 왕복에서 드러난 병합 행 높이, 머리말·각주 위치 복원과 새 각주의 잘못된 스타일 참조도 별도 항목으로 추적한다. 커서 지문은 대상 소유·문단·주변 문맥 검증이며 전역 원시 레코드 보존을 대신하지 않는다. 미관측 필드·개체·원시 데이터는 읽기 전용으로 유지한다.

## 검증과 남은 작업

[통합 검증 기록](evidence/state-storage-2026-10-16/verification-summary.json): 단위 검사 804개, 제공자·서버 합성 검사 52개, 실제 WASM 엔진 검사 430개, Edge 브라우저 검사 312개가 통과했다. 엔진·브라우저 결과는 52개 검증 묶음이며, 기능 완료 개수나 한글 전체 호환률을 뜻하지 않는다. TypeScript 오류는 없고 모듈 경계 9개·소스 303개의 검사도 통과했다. 실제 외부 LLM 호출은 수행하지 않았다. 저장 실패 검사는 자체 작성한 문서, 격리된 브라우저와 임시 OPFS 파일에만 장애를 주입한다. 사용자 문서·실행 창·연결 키는 검증 대상으로 사용하지 않는다.

- 한글 2024의 실제 저장 재열기·지면·모든 대화상자 조합 비교는 마지막 일괄 검수로 남긴다.
- Windows 파일 선택창, ACL·읽기 전용·공유 잠금, 강제 프로세스 종료 복구는 OPFS와 정상 재실행 검증과 구분한다.
- HML 엔진 경로와 일반 XML 탭·서식·문서 관리 UI는 같은 기능이 아니다. 전체 XML 입출력은 미완료로 유지한다.
- 전자서명·변경 추적·모든 OLE·미해석 원시 레코드의 완전한 보존은 현재 검사 범위 밖이다.
- 전체 상위 범위의 완료는 좁은 하위 작업의 구현·자동 검사 완료와 별도로 관리한다.

## 실행과 한글 검수 준비

프로젝트 루트의 `build/jueony-storage-20261016/Start-Review.cmd`를 실행한다. 이번 검수 묶음은 `http://127.0.0.1:4326/`을 사용하며 이전 실행 서버를 종료하지 않는다. Windows 정책으로 Rust exe 실행이 차단될 때도 같은 폴더의 cmd 진입점을 사용할 수 있다.

`review-documents/storage/`에 직접 작성한 HWP/HWPX 저장 결과를 기능별로 담았다. 우선 `save-browser/readback-success-hwp.hwp`, `readback-success-hwpx.hwpx`와 `saveas-*` 네 조합을 한글 2024에서 열어 내용·서식·쪽 수를 확인한다. 이어 `merged-row-browser/`, `visible-browser/`, `story-browser/`의 예제로 병합 행 높이·후속 본문 위치·머리말/각주를 확인한다. 자동 검사에 일부러 손상시킨 저장 실패 파일은 검수 문서로 배포하지 않고 해시만 기록한다.

검수 시 원본 대신 별도 복사본을 사용하고, 한글에서 재저장한 결과와 차이는 별도 근거로 남긴다. 한글 직접 검수 결과를 아직 통과로 표시하지 않았다.
