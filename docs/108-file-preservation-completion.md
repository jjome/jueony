2026-10-17. [기능별 작업표](features/05-files-storage-recovery.md) · [종합 현황](jueony-progress.md). 이번 범위는 HWP/HWPX 저장 연결, 취소·실패 복구, 현재 재현 가능한 겹침 배치 결함이다. 한글 2024의 모든 파일 메뉴·XML 서식·호환성을 완료했다는 뜻은 아니다.

## 수정한 결함

| 항목 | 수정 후 동작 | 유지한 보호 |
| --- | --- | --- |
| Windows Rust 파일 읽기 | 외부 수정 바이트를 읽어도 저장 기준 지문을 자동 채택하지 않음 | 명시적 새 연결 또는 검증한 저장만 기준 변경 |
| Windows Rust 저장 확인 | 교체 뒤 실제 파일 바이트를 읽고 일치한 경우에만 기준 갱신 | 전후 충돌 검사·임시 파일·sync·실패 보고 |
| 다운로드 저장 취소 | 최종 ‘저장 확인’ 전에는 이름·원본 연결·출력 형식을 변경하지 않음 | 열린 내용·dirty·undo·기존 복구본 유지 |
| 다운로드 다른 형식 저장 | 최종 승인 후 옛 원본 handle을 분리하고 다운로드 출력 형식 유지 | 이후 Ctrl+S가 옛 원본으로 돌아가지 않음 |
| 복구본 폐기 실패 | IDB 복구본 삭제 성공을 폐기 commit으로 취급 | 삭제 실패 시 탭·dirty·undo·열린 내용과 기존 복구본 유지 |
| 겹침 표 후속 여러 줄 본문 | 직접 본문 열의 줄 소유·연속 원문·문자 시작·원시 줄 위치가 일대일 확인될 때 저장 사본에 줄별 위치 기록 | 라이브 문서·원시 소유·미해석 자료를 바꾸지 않음 |
| 겹침 표의 캡션 | 본문 줄과 캡션/표 내부 story의 소유를 분리 | 캡션·중첩 control payload의 원시 차이 검사 |
| 양수 원점 간격 | 앞 표 편집 때문에 아직 소비하지 않은 원본의 양수 간격을 잃지 않도록 제한된 조판 경로 보완 | 원본 좌표를 낮추거나 clamp하지 않고 한쪽/한단·인접 통째 표·저장 원점 ladder 검사 |

다운로드는 브라우저가 디스크 기록 완료를 보증하는 API를 제공하지 않는다. 실제 파일을 확인한 사용자의 최종 승인 흐름은 유지한다. 새 문서/파일 열기는 문서 generation이 바뀌므로 과거 다운로드 형식 기억을 자동으로 무효화한다. 복구 후에는 실제 복구 파일의 형식이 새 문서의 기준이 된다.

## 보존 경계

기존 `assertOverlapSaveLayout`의 전체 공개 개체·셀·본문 배치 비교와 0.2 오차 기준은 변경하지 않았다. 새 원점 처리는 한쪽·한단, 원시 호스트가 확인된 인접 통째 표, 지원하는 본문 줄 partition에 한정한다. 혼합 크기로 줄 partition이 달라진 원본, 필드·책갈피·다단·중복 주소·음수/절대 배치·원점 불명확 원본을 지원 성공으로 바꾸지 않는다.

원시 CFB/압축 Section0을 독립적으로 읽어, 같은 편집을 수행한 이전 엔진의 저장 결과와 비교한다. 모든 비본문 stream, 레코드 topology, 캡션/중첩 control payload는 같고 허용한 본문 LINE_SEG의 vpos 필드만 바뀌는지 검사한다. 이는 이번 패치의 추가 변경 범위를 증명하며, 이전 엔진 자체가 미해석 원본 전체를 완전히 보존한다고 보증하는 검사는 아니다.

## 통합 검증

최종 정식 엔진 `c3706ce8cab54953`과 같은 프런트엔드에서 단위 **815개**, 실제 WASM **458개**, Edge **338개**, 실제 Windows 파일 저장 **10개**가 통과했다. 58개 검증 묶음이며 기능 개수나 전체 한글 완료율은 아니다. TypeScript 오류 0, 모듈 경계 9개·소스 306개도 통과했다. 수행한 결과는 [검증 요약](evidence/file-preservation-2026-10-17/verification-summary.json)에 기록한다. 사전 private 후보 검증을 최종 결과로 대체하지 않는다. 이전 실행본의 검사 개수를 새 버전의 검사 개수에 합산하지 않는다.

검사 경계는 다음과 같다.

- 같은 최종 실행본의 단위·TypeScript·모듈 경계와 저장·다운로드·닫기·복구 회귀.
- 실제 WASM의 저장·재열기·반복 저장·undo/재적용, 배치와 의미·허용 원시 바이트 차이.
- 실제 Edge에서 속성 변경, undo/redo, 원본 파일 저장 후 화면 재열기, 실패 상태 보존.
- 실제 Windows 파일에서 생산 Rust 코드의 읽기 전용·독점/교체 잠금·실제 바이트·외부 변경 보호. [107번 범위](107-native-file-storage.md).
- 별도 Edge 프로필의 HWP/HWPX 강제 종료 복구와 새 checksum 기록. [106번 범위](106-recovery-integrity.md).

특수 영역 복원 검수는 선택 직후의 동기 저장 뷰와 비동기 스크롤 이후의 뷰를 비교하는 사전조건 race가 있었다. controlled trace로 footer의 저장/비교전/복원후 scrollY 0/61/0, 각주 0/36/0을 재현했다. 선택 후 두 프레임을 기다리고 저장 뷰와 비교 전 뷰의 동일성을 먼저 검사하도록 수정했다. 기존 전체 상태·스크롤·재실행 deepEqual 검사는 유지했으며 최종 7개가 통과했다. 실패했던 첫 결과와 대조 trace는 별도 진단 근거로 보존하고 통과 수에 합산하지 않았다. 생산 복원 코드 변경은 없다.

## 실행

`build/jueony-file-preservation-20261017/Start-Review.cmd` (4328), 프로필 `file-preservation`. `review-documents/file-preservation/`에서 `overlap-body-native/`의 여러 줄·캡션 예제, `overlap-positive-native/`의 양수 간격 예제와 `native-windows/`의 두 형식 원본/수정 예제를 한글 2024 검수용으로 사용한다. 다운로드 검수의 실제 내려받은 파일도 결과와 해시로 추적한다. 기존 실행 서버와 문서는 유지한다.

## 다음 마감 순서

1. 기존 검수용 원본을 보존한 채 `review-documents/file-preservation/`의 사본을 한글 2024에서 연다. 여러 줄·캡션·양수 간격과 두 형식 원본/수정본을 우선 비교한다.
2. 쪽 수·본문 위치·표/캡션 배치·인쇄 미리 보기를 대조하고, 한글에서 다시 저장한 사본까지 재열기 결과를 기록한다. 완료 근거가 확보된 항목만 CSV의 한글 검증과 전체 검증 상태를 변경한다.
3. Windows 실제 선택창→저장→재실행 전체 GUI를 검수한다. 현재 통과한 Rust 파일 검사를 이 GUI 검수의 완료로 대체하지 않는다.
4. N001의 혼합 크기·다단·복합/불명확 원점은 재현 원본과 기대 결과부터 확정한다. 현재 거절하는 보호 검사를 완화해 성공으로 표시하지 않는다.
5. 일반 XML 서식 등 별도 미구현 상위 기능은 독립 작업으로 유지한다.

## 남은 범위

- 실제 한글 2024 재열기·인쇄·쪽 배치 비교는 요청에 따라 마지막 일괄 검수로 남긴다.
- 실제 Windows 선택창부터 저장까지의 GUI, 전체 ACL 조합, OS 전원 차단/디스크 장애를 검증한 것은 아니다. 읽기 전용·공유 잠금은 이번에 실제 Windows 파일에서 확인했다.
- 미지원 복잡 배치와 원시/특수 story는 보호 검사에서 거절될 수 있다. 기존 복구본과 열린 편집 내용은 유지한다.
- 일반 XML 서식/스키마 UI, 모든 한글 파일 메뉴·개인 정보/이력 편집·새 창과 새 탭의 완전한 구분은 이번 저장 결함 수정 범위 밖이며 작업표에서 미완료로 유지한다.
- Tauri의 함수형 file handle은 IDB에 직렬화되지 않으므로 재실행 뒤 원본 자동 연결을 보증하지 않는다. 현재 브라우저 파일 handle 복원/재권한 및 복구 문서 다른 이름 저장 경로와 구분한다.
- 이번 변경은 Agent에 임의 디스크 쓰기나 자동 저장 권한을 추가하지 않는다.
