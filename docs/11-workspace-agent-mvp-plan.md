# Workspace·채팅·AI 직접 편집 MVP 작업 계획

작성일: 2026-10-09

코드 검토 기준: Jueony `2d6f491`, rhwp `1a76570e833917d15817415a53c09ad61ab3203f`, `@rhwp/core@0.8.7`.

상태: **요구사항과 작업 목록만 추가했다. 아래 M00~M12는 모두 구현 전이며 새 실행 검증을 수행하지 않았다.**

## 1. 제품 방향과 기존 계획의 변경

Jueony는 업무별 자료와 대화를 관리하고, 가운데 채팅에서 지시하면 오른쪽의 실제 한글 문서를 AI가 직접 편집하는 프로그램이다. 사용자와 AI는 같은 열린 문서를 다룬다. 최종 작업 범위는 내용·구조·서식·표·개체·쪽 설정·저장이다.

기본 흐름은 **요청 → 문맥 구성 → LLM → 명령 검증 → 직접 적용 → 결과 확인·되돌리기**다. 매번 문단을 선택하거나 제안마다 승인하는 절차를 기본 흐름에 넣지 않는다. 변경 비교는 적용 결과를 확인하는 보조 기능이다. AI가 지원하지 않는 작업은 실행하지 않았다고 명확히 표시한다.

이번 사용자 요청의 마지막 지시는 작업 문서 갱신이다. 구현·API 호출·빌드·배포는 지금 시작하지 않는다. 이후 구현은 이 문서와 [기본 편집기 보강 계획](10-basic-editor-work-plan.md)을 함께 따른다.

우선순위는 다음과 같이 바꾼다.

- 이 문서는 최신 MVP의 범위와 순서를 정한다. 01의 제품 요구사항도 이에 맞춰 갱신한다.
- 03·05의 단일 문단 mock/승인 경로는 초기 기술 검증 기록이다. 이를 제품 전체의 제약이나 새 MVP의 필수 화면으로 적용하지 않는다.
- 10의 E00~E12는 기본 편집기 보강 목록으로 유지한다. MVP에 필요한 저장·명령·문서 격리 부분을 먼저 연결하며, 모든 서식·인쇄 보강 완료를 MVP의 선행 조건으로 만들지 않는다.
- 실제 한글의 복잡한 문서 검증은 독립 관문이다. 개발 중 구조 검사와 실제 한글 검수를 구분한다.

## 2. MVP의 필수 범위와 후속 범위

| 구분 | 이번 MVP | 후속 확장 |
| --- | --- | --- |
| 업무 | workspace 생성·전환·이름, 여러 폴더 연결, 최근 문서/상태 복원 | 기관 공통 자료, 공유 workspace, 세부 보관 정책 UI |
| 대화 | workspace 안의 채팅 생성·전환·이름 변경, 메시지·실행 이력 영속화 | 대화 분기·공유·검색 고도화 |
| 자료 | 연결한 폴더의 계층 탐색, 파일/폴더를 요청 참고 자료로 지정 | 자동 분석·RAG·벡터 DB·OCR·폴더 감시 |
| 문서 | 기존 HWP/HWPX 열기·수동 편집·저장, 새 문서, 미저장 본문 읽기 | 문서군 전체의 조판/개체 호환성 확대 |
| AI 편집 | 여러 본문 위치 읽기, 본문 삽입·교체·삭제, 요청 결과·되돌리기 | 문단 이동·복잡한 표·개체·쪽 설정 자동화 |
| 표·서식 | 기존 엔진 경로를 실제 검증한 최소 명령만 추가 | 모든 편집 기능을 AI 도구로 확장 |
| 모델 | 실사용 가능한 provider adapter 1개, 연결 설정과 모델 선택 분리 | HyperCLOVA X 고유 규격 등 추가 adapter |
| 실행 제어 | 1회 문맥 구성·생성·검증·적용, 취소·충돌·부분 실패 기록 | 관찰/판단/실행 loop, 자동 재시도·자기평가 |
| 배포 | 기존 Windows 로컬 실행 묶음 | 기관 설치·업데이트·전자결재 연계 |

제품 예시의 제공 범위도 나눈다.

- “작년 계획서를 참고해 올해 초안 작성”: 선택한 자료의 지원 텍스트를 읽어 새 문서 본문을 만드는 필수 시나리오. 자료를 읽지 못하면 참고했다고 답하지 않는다.
- “추진 일정은 표로 정리”: 표 생성·셀 채우기·undo·저장을 검증한 뒤 지원하는 추가 시나리오. 텍스트 목록을 만든 경우 표 생성 성공이라고 하지 않는다.
- “두 번째 항목을 앞으로 옮기고 제목 서식 통일”: 구조 이동과 서식 명령 각각의 지원 여부를 표시한다. 첫 필수 범위의 단순 교체로 문단·개체 이동을 흉내 내지 않는다.

이번 확인은 정적 코드 검토다. 기존 통과 기록을 새 MVP가 동작한다는 증거로 사용하지 않는다.

| upstream `document-agent/{controller,contract}.ts` | 기존 명령은 본문 한 문단 교체, 길이·제어문자·원문·서식·주변 문맥 검사에 제한된다 | 검증 원칙을 재사용하되 제품 명령 계약을 이 v1에 고정하지 않음 |

여기서 `jueony-workspace`라는 기존 DOM/CSS 이름은 편집 화면의 배치 요소다. 업무별 영속 workspace 구현으로 계산하지 않는다. 참조 경로는 `upstream/rhwp-source/rhwp-studio/src/`이며 무단 편집·자동 최신화하지 않는다.

## 4. 화면과 상태 소유권

```text
┌────────────────────┬──────────────────────┬────────────────────────┐
│ workspace 선택     │ 선택한 채팅           │ 활성 HWP/HWPX 문서     │
│ 채팅 목록          │ 메시지·진행·결과      │ 기존 편집기·도구·탭    │
│────────────────────│                      │ 사용자/AI 동일 상태    │
│ 조절 가능한 경계   │ 참고 자료·모델 선택   │ 변경 확인·undo·저장    │
│ 연결한 폴더 트리   │ 입력창·실행·취소      │                        │
└────────────────────┴──────────────────────┴────────────────────────┘
```

왼쪽의 채팅 목록/폴더 트리 높이는 드래그와 키보드로 조절하고 로컬에 복원한다. 좁은 화면에서는 편집기 폭을 확보할 수 있도록 패널 접기/폭 조절을 제공한다. 폴더에서 HWP/HWPX를 여는 동작과 참고 자료로 지정하는 동작을 구분한다.

- Workspace가 폴더 연결·채팅·작업 문서를 소유한다. DocumentSession이 실제 iframe/engine을 식별한다.
- 같은 workspace의 채팅은 자료 폴더를 공유하지만 메시지와 실행은 공유하지 않는다. 선택하지 않은 채팅의 메시지를 프롬프트에 넣지 않는다.
- 문서는 workspace에 속하고 요청은 시작 시 선택한 문서를 고정한다. 서로 다른 채팅이 같은 문서를 대상으로 작업하는 것은 가능하되 MVP에서는 실행을 하나씩 직렬화한다.
- workspace/채팅/활성 문서를 바꾸면 진행 중 생성은 취소한다. 적용 중인 짧은 임계 구간에서는 전환을 잠시 제한한다. 늦게 도착한 응답은 새 화면에 적용하지 않는다.
- 다른 workspace의 열린 탭·복구 초안은 숨김/보존하며 현재 문맥에 넣지 않는다. 전환 때문에 미저장 편집을 버리지 않는다.

## 5. 최소 기술 구성과 책임 경계

### 기존 실행 환경을 유지하는 기본안

TypeScript shell·로컬 Studio/WASM·Rust 런처를 유지한다. React 전환, Python 전체 서비스 통합, Tauri 빌드 성공을 MVP의 전제로 두지 않는다.

MVP의 로컬 업무 메타데이터는 IndexedDB를 기본안으로 한다. 지원되는 Edge/Chrome에서 DirectoryPicker로 폴더 핸들을 등록하고 동일 origin/profile에서 핸들과 workspace를 복원한다. 브라우저가 권한을 다시 요구하면 사용자 동작으로 재연결한다. 경로 문자열만 저장해서 접근이 복원됐다고 표시하지 않는다.

현재 정적 런처에는 모델 호출 기능이 없다. 기본 구현 후보는 Rust의 제한된 로컬 LLM 호출 서비스이며, 기존 정적 서버와 명시적으로 통합한다. HTTP/TLS는 유지보수되는 라이브러리를 사용하고 기존 간단한 정적 HTTP 파서를 임의 외부 프록시로 확장하지 않는다. 실제 빌드 가능성과 인증 경계는 M00/M06에서 확인한다. 브라우저 직결은 해당 endpoint의 CORS·자격증명 취급·CSP가 검증된 경우에만 별도 판단하며 무조건적인 `connect-src *`로 우회하지 않는다.

### 계층과 제안 파일 위치

아래 경로·타입은 **신규 구현안**이며 현재 존재하는 API가 아니다. 서로 다른 책임이 있을 때만 모듈을 나누고 빈 framework를 만들지 않는다.

| 계층 | 제안 위치(앱 src 기준) | 책임 |
| --- | --- | --- |
| UI | `shell.*`, `workspace-ui.ts`, `chat-ui.ts` | 선택 상태·메시지·진행·결과 표시 |
| 업무 저장 | `workspace-store.ts` | workspace/chat/message/run 영속화와 소유권 검사 |
| 로컬 자료 | `folder-access.ts`, `reference-reader.ts` | 폴더 핸들·트리·명시 자료 읽기 |
| Context | `agent/context.ts` | 현 채팅·문서 snapshot·지정 자료를 공통 입력으로 구성 |
| 실행 제어 | `agent/run-once.ts` | 1회 실행·취소·상태 전이·중복 방지 |
| LLM Port | `llm/port.ts`, `llm/config.ts` | 제공자 중립 요청/응답/오류, 모델 설정 |
| Provider 등록 | `llm/registry.ts` | 실제 adapter와 지원 capability 선택 |
| Provider Adapter | Rust LLM 서비스의 provider 모듈 | 제공자 HTTP 요청·인증·응답/오류 변환; 공통 port 계약을 구현 |
| 문서 Tool | `editor-bridge.ts`, `agent/edit-schema.ts` | 같은 engine 읽기·명령 검증·실행·receipt |
| 결과 기록 | `agent/run-record.ts` 또는 업무 저장 모듈 | 실제 적용 결과·자료 범위·실패·취소 저장 |

의존성은 `UI → Application/Agent → LLM Port ← Provider Adapter`다. 로컬 HTTP client/서버는 이 port를 전달하는 transport다. UI/Agent가 제공자 SDK 타입, URL 경로 규칙, JSON 응답 필드를 해석하지 않게 한다.

RAG는 나중에 Context 공급 기능에 추가한다. loop는 실행 제어에 추가한다. 둘을 provider 내부에 넣지 않는다. 첫 버전은 호출 한 번이며 자동 재시도나 모델 응답 복구용 추가 호출도 하지 않는다.

### 데이터 계약

| 엔터티 | 최소 필드 | 불변 조건 |
| --- | --- | --- |
| Workspace | id, name, createdAt, updatedAt, activeChatId, lastDocumentId | 화면 이름과 독립된 안정적인 ID |
| FolderLink | id, workspaceId, label, handleRef, permissionState | 원본 연결만 보관. 해제는 원본 삭제가 아님 |
| Chat | id, workspaceId, title, selectedModelConfigId | workspace 소유권을 조회/쓰기 모두 검사 |

| DocumentSession | id, workspaceId, sourceRef?, generation, revision, dirty, recoveryRef? | 실제 engine과 연결. 복구본은 원본 자동 덮어쓰기 금지 |

IndexedDB schema version·migration과 transaction을 둔다. 저장 실패 시 영속화 성공을 표시하지 않는다. 재시작하면 진행 중이던 실행은 `interrupted`로 복원하며 자동 재실행·재적용하지 않는다.

## 6. 문맥과 자료 범위

- 현재 문서는 저장 여부와 무관하게 실제 engine에서 읽는다. snapshot 전후 revision이 다르면 다시 읽거나 명시적으로 실패시킨다.
- snapshot에는 문서 전체의 순서·본문 텍스트·대상 식별자·기본 구조·읽기/편집 가능 범위를 둔다. 표·머리말·개체 등은 읽을 수 있는 텍스트와 미지원 구조를 구분한다. 빠진 내용을 읽었다고 주장하지 않는다.
- 선택한 파일 또는 폴더만 해석한다. 폴더 선택은 요청 시작 시 하위 지원 파일 목록으로 확정하고 이름·상대 경로·개수·읽은 범위·실패/제외 이유를 표시한다.
- 우선 참고 형식은 HWP/HWPX와 UTF-8 TXT/Markdown이다. HWP/HWPX는 기존 엔진의 읽기 전용 파싱을 재사용하되 편집 중인 문서를 교체하지 않는다. PDF/DOCX/XLSX/이미지 OCR은 초기 미지원으로 표시한다.
- 현재 열린 파일을 참고 자료로도 지정한 경우 현재 문서 snapshot을 우선하고 디스크의 오래된 내용과 중복 전송하지 않는다.
- 파일 수·바이트·문맥 한도를 둔다. 한도 초과는 범위를 줄여 달라고 안내하거나 사용자가 확인 가능한 제외 목록을 만든다. 앞부분만 조용히 잘라 전체 분석이라고 표시하지 않는다.
- 본문 전체를 한 요청에 넣을 수 없는 문서는 제한을 안내한다. 이번 단계에서는 RAG나 자동 분할 호출로 우회하지 않는다.
- 자료에는 source ID·내용 해시/수정 시각·읽은 범위·지원되는 논리 위치를 남긴다. LLM이 임의로 만든 출처 ID는 검증에서 거부한다. 확실하지 않은 쪽수를 만들지 않는다.
- 폴더 import는 목록 탐색을 위한 연결이다. 읽지 않은 파일에 분석 완료 표시를 하지 않는다. 제외·접근 거부·손상 파일이 있으면 명시하며 필요한 핵심 자료를 읽지 못한 요청을 성공한 참고 작업으로 처리하지 않는다.
- 원문과 참고 자료는 비신뢰 데이터로 구획한다. 그 안의 “다른 폴더를 읽어라/키를 출력하라”를 권한이나 system 지시로 바꾸지 않는다. 모델 결과는 실행 가능한 코드로 평가하지 않는다.

## 7. 문서 명령·충돌·되돌리기 계약

### 제품 명령의 초안

`EditBatchV1`은 제품이 새로 정의할 내부 계약이다. upstream 단일 문단 v1에 임의 필드를 추가하지 않는다.

- 앱이 부여하는 envelope: runId, workspaceId, documentSessionId, generation, baseRevision, schemaVersion.
- 모델이 반환하는 payload: 설명, 허용된 operation 목록, 사용하는 source ID. 모델이 쓴 문서 ID/revision을 권한 근거로 사용하지 않는다.
- 필수 operation: `create_document`, `insert_body_paragraphs`, `replace_body_text`, `delete_body_text`.
- `create_document`는 새 session 생성 요청이다. 기존 미저장 문서를 덮어쓰지 않는다. 기존 문서 편집과 섞인 묶음은 첫 버전에서 거절한다.
- 대상은 snapshot이 제공한 참조다. 없는 문단·범위 밖 offset·겹치는 편집·예상 원문 불일치를 사전 검증한다. 모델에게 엔진 함수명·임의 파일 경로·임의 명령 실행 권한을 주지 않는다.
- 삽입/삭제에 따른 주소 이동을 고려해 기준 snapshot의 논리 대상에 매핑한다. 초기 구현은 겹침/새로 생성된 대상을 재참조하는 복잡한 묶음을 거부할 수 있다.
- 글자 단위는 엔진 계약을 확인해 통일한다. 한국어·이모지/서로게이트 문자와 문단 경계를 검사한다.
- 문단 구조 삭제와 문단 안 텍스트 삭제는 구분한다. 첫 삭제 명령은 검증된 본문 텍스트 범위이며 개체/필드를 포함한 구조 삭제를 암묵적으로 수행하지 않는다.
- 여러 본문 위치를 한 요청에 처리하는 것은 필수다. 단일 문단 제한으로 되돌려 제품 완료로 처리하지 않는다.
- 표·서식 operation은 capability 검사와 실제 편집/저장/undo 검증 후 등록한다. 일반 automation registry 전체를 LLM에 노출하지 않는다.
- 저장은 기존 저장 서비스를 통해 사용자가 실행한다. 자동 저장 도구는 후속 capability로 둘 수 있으며 MVP의 직접 편집 성공이 곧 원본 파일 저장 성공은 아니다.

### 적용 순서

1. schema·지원 명령·개수/크기·자료 ID·대상·예상 원문·소유권을 전체 묶음에 대해 검증한다.
2. 생성 중 사용자의 편집은 허용한다. 적용 직전에 generation/revision을 다시 비교하고 다르면 `conflict`로 끝낸다. 사용자에게 새 요청으로 다시 실행하도록 안내한다.
3. 적용 직전 짧은 mutation gate를 획득해 사용자 입력·저장·다른 실행과 겹치지 않게 한다. IME 조합이 진행 중이면 조합이 안정되기 전 적용하지 않는다.
4. 기존 command/history/snapshot을 이용해 같은 열린 engine을 바꾼다. 채팅 텍스트나 디스크 파일만 바꿔 성공 표시하지 않는다.
5. 실제 문서 상태·렌더 결과·revision을 확인하고 receipt를 만든 뒤 gate를 해제한다.
6. 결과는 모델의 자기보고가 아니라 실행 receipt를 기준으로 채팅에 표시한다.

### 실패와 요청 단위 되돌리기

가능하면 하나의 요청을 엔진 snapshot/undo 한 단위로 기록한다. 기존 history의 transaction·render 복구를 실제 WASM에서 시험한 후 사용한다. 단순히 실행한 명령 수만큼 Ctrl+Z를 보내는 방식은 채택하지 않는다.

receipt는 base/result revision, 명령별 적용 결과, 변경 전후 요약, undo 연결, rollback 결과를 포함한다. 실패 상태는 `failed_no_change`, `failed_rolled_back`, `failed_partial`로 구분한다. rollback 자체가 실패하면 남은 변경 범위와 복구 가능 상태를 표시하고 추가 AI 적용을 중단한다. 원본 디스크에는 자동 저장하지 않는다.

요청의 결과가 최신 변경일 때 요청 단위 되돌리기를 제공한다. 이후 사용자 편집이 있으면 오래된 전체 snapshot으로 덮어쓰지 않는다. 그 경우 일반 undo를 사용하거나 되돌림 불가 사유를 안내한다. 새 문서 작성의 되돌리기도 사용자 추가 입력을 삭제하지 않도록 같은 조건을 적용한다.

## 8. 실제 LLM 연결과 실행 제어

### Port·Registry·설정

Port는 내부 Message, Context, 지원 편집 schema, 생성 옵션, AbortSignal을 받아 공통 GenerationResult/LLMError로 반환한다. 제공자 전용 role·tool-call·usage 객체를 UI 타입으로 사용하지 않는다. 편집 payload의 의미 검증은 Agent/문서 Tool의 책임이다.

첫 adapter의 기본 후보는 **OpenAI 호환 Chat Completions**다. 이것은 프로토콜 후보이며 특정 기관이나 HyperCLOVA X의 호환성을 확인했다는 뜻이 아니다. 실제 provider·endpoint·모델·키는 아직 제공되지 않았다. 구현 착수 시 연결 정보를 확인하고 고유 규격만 지원하면 해당 adapter 하나로 대체한다.

설정 화면은 연결 이름, adapter, endpoint, 모델 ID, 연결 상태를 구분한다. 모델 목록 API가 없으면 사용자가 모델 ID를 입력/등록한다. 임의의 미지원 provider 목록이나 존재를 확인하지 않은 모델을 동작하는 선택지처럼 표시하지 않는다. 요청 시작 시 설정 snapshot을 고정하며 선택 변경은 다음 요청에 반영한다.

mock은 명령 계약과 오류 검사용이다. 실제 provider 연결 성공으로 표시하지 않으며 mock만으로 M07/M12를 통과시키지 않는다.

### 인증과 전송 경계

API 키는 MVP에서 실행 세션 메모리에만 보관하는 방식을 우선한다. 재시작 후 재입력을 요구할 수 있다. 영속 보관을 추가한다면 OS 비밀 저장소를 사용하고 실패 시 평문으로 폴백하지 않는다. 키는 ModelConfiguration/채팅/RunRecord/IndexedDB/일반 로그에 넣지 않는다.

로컬 호출 서비스는 loopback 전용이며 프로세스 세션 인증과 origin/Host 검사를 한다. 세션 토큰을 URL·로그에 남기지 않는다. 설정된 허용 endpoint 외에는 요청하지 않고 임의 URL fetch 도구를 제공하지 않는다. redirect로 다른 서버에 본문/키를 보내지 않으며 TLS 검증을 끄지 않는다. 문서 iframe에 provider 키를 전달하지 않는다.

401/403, rate limit, timeout, 연결 단절, 취소, 응답 크기 초과, 깨진 JSON, 미지원 모델/명령을 공통 오류로 바꾼다. 서버 오류 본문에 키/인증 헤더가 섞여 있어도 진단이나 채팅에 그대로 저장하지 않는다. 실제 연결 시험은 합성 자료로 수행하고 요청한 모델 ID·endpoint·결과를 비밀 없이 기록한다.

### 단일 실행 상태

`queued → preparing_context → generating → validating → applying → completed`

분기: `cancelled`, `conflict`, `failed_no_change`, `failed_rolled_back`, `failed_partial`, 재시작 시 `interrupted`.

전송과 취소의 runId를 유지하고 늦은 응답을 무시한다. 적용 중 취소는 명령의 안전한 경계에서 처리하고 이미 생긴 변경/rollback 여부를 기록한다. 명령 묶음의 중복 응답·중복 클릭은 같은 runId에 두 번 적용되지 않아야 한다. 원격 작업을 취소하지 못했더라도 로컬 문서에 뒤늦게 적용하지 않는다.

완료: 기존 기능/추가 adapter/미지원 기능을 구분한 capability 표, 사용할 런타임·저장소·provider 규격 결정. 미제공 연결 정보는 실제 호출 검증의 차단 조건으로 남기고 독립 구현은 진행한다.

### M01. 업무 저장과 소유권

workspace 생성·전환·이름 변경, 채팅 생성·전환·이름 변경, 메시지·실행·최근 문서 참조를 구현한다. versioned schema와 저장 실패 처리를 둔다. 조회·쓰기 API 모두 workspaceId/chatId를 검증한다. UI에서 목록을 숨기는 것만으로 격리를 구현하지 않는다.

완료: W-A/W-B 각각 두 채팅의 내용과 실행 기록이 분리되고 재시작 후 복원된다. 같은 이름의 업무/채팅도 ID로 구별한다. 진행 중 실행은 재시작 후 interrupted가 된다.

### M02. 연결한 폴더와 자료 지정

DirectoryPicker 등록, 여러 root, 하위 트리의 필요한 시점 열기, 새로고침, 연결 해제, 파일/폴더 참고 지정 UI를 구현한다. 원본 복사·이동·삭제는 하지 않는다. 삭제/이동/권한 거부/재연결과 같은 이름의 다른 폴더를 처리한다. 재연결된 폴더가 다른 원본이면 자동으로 같은 자료라고 합치지 않는다.

완료: 두 root의 동명 파일이 구별되고 해제 전후 원본 내용/해시가 같다. 권한 재승인 상태를 표시한다. API 미지원 실행 환경에서는 연결 가능하다고 표시하지 않고 지원 런타임을 안내한다.

### M03. 업무 화면과 문서 연결

shell에 왼쪽 업무/채팅/트리, 가운데 채팅, 오른쪽 기존 editor iframe을 배치한다. 왼쪽 세로 경계 조절과 상태 복원을 구현한다. 트리 문서 열기·새 문서·탭 선택을 workspace의 DocumentSession에 연결한다. 채팅 변경과 문서 변경의 역할을 구분한다.

완료: 채팅과 실제 편집기를 동시에 사용할 수 있고 기존 저장·undo·닫기 보호가 유지된다. 오른쪽에 열린 다른 workspace의 문서가 현재 요청에 결합되지 않는다.

### M04. 열린 문서 읽기

host API에 문서 ID/generation/revision과 일관된 전체 snapshot을 추가한다. 본문 모든 위치와 지원되는 구조를 순서대로 제공한다. 표/필드/개체의 누락·읽기 전용·편집 가능 상태를 구분한다. 읽는 동안 문서가 바뀌면 일관성이 깨진 snapshot을 반환하지 않는다.

완료: 저장 전 최신 내용이 포함되고 두 개 이상의 떨어진 문단에 안정적으로 주소를 부여한다. 페이지의 DOM 텍스트나 디스크 재읽기를 현재 문서의 기준으로 쓰지 않는다.

### M05. 명시 자료와 Context

HWP/HWPX/TXT/Markdown 추출, 폴더 선택의 파일 목록 확정, 내용 크기/형식 제한, 출처 manifest를 구현한다. 현재 채팅의 메시지 범위와 현재 문서, 이번에 지정한 자료만 합친다. 채팅 길이 제한도 표시하고 보이지 않게 다른 채팅을 보충하지 않는다.

완료: 모델에 실제 전달한 파일/범위가 확인되며 미지원·손상·한도 초과가 표시된다. 자료의 악성 지시로 다른 폴더 읽기·키 접근·명령 allowlist 우회가 발생하지 않는다.

### M06. Port·Registry·모델 설정·호출 경계

공통 타입과 최소 registry를 만든다. frontend 공통 요청을 로컬 서비스로 전달하고 provider 전용 형식은 adapter에서만 처리한다. endpoint 허용·인증·취소·오류 redaction을 포함한다. 저장되는 설정에는 비밀을 넣지 않는다.

완료: fake port를 이용해 UI/Agent가 특정 provider JSON/SDK에 의존하지 않는 것을 확인한다. 인증 없는 호출·허용되지 않은 origin/Host·endpoint·redirect를 거부한다. static 서버의 기존 자산 제공도 유지된다.

### M07. 실제 provider adapter와 모델 선택

실제 선택한 규격으로 단일 생성 호출을 구현한다. 인증, model ID, structured output 수신/파싱, 공통 오류, timeout·취소를 연결한다. 자동 fallback endpoint/모델/재시도를 넣지 않는다. 모델 목록 미제공 시 모델 ID 직접 등록 경로를 제공한다.

완료: 등록한 provider/모델 선택이 실제 요청에 반영된다. 하나의 실제 연결이 합성 자료로 성공하고 잘못된 키/모델/응답을 처리한다. 두 번째 등록 모델을 사용할 수 없으면 선택 전달은 계약 검사로 확인하고 실제 검증 범위를 구분한다.

### M08. 본문 변경·undo·부분 실패

제품 명령 schema와 target mapper를 구현한다. 전체 batch 검증, revision 충돌, 중복 적용 차단, mutation gate, render 확인, receipt와 요청 단위 undo를 연결한다. 새 문서 작성과 여러 본문 위치 삽입/교체/삭제를 수행한다.

완료: 수동 선택 없이 여러 본문 위치가 실제로 바뀐다. 중간 명령 실패 시 무변경/복구/부분 변경이 구분된다. 후속 사용자 편집을 보존하며 저장 후 다시 읽어 기대 내용을 확인한다. 이 핵심이 미완료이면 단일 문단 데모를 MVP 완료로 보고하지 않는다.

### M09. Agent 단일 실행

Context, Port, 명령 검증, 문서 Tool, RunRecord를 연결한다. 실행/취소/오류 상태와 사용 자료·실제 변경 결과를 가운데 채팅에 표시한다. 일반 요청은 검증 후 직접 적용하며 매번 승인 모달을 넣지 않는다. 실행 결과 비교와 되돌리기를 제공한다.

완료: 요청 1개가 LLM 생성 1회와 검증된 batch 1회로 이어진다. 생성 중 사용자가 편집/전환/취소하면 오래된 결과가 적용되지 않는다. 작업 기록은 원래 채팅에만 남는다.

### M10. 표·서식의 작은 확장

기존 E05/E06 명령 중 단순 표 만들기·셀 채우기 또는 제목 서식 적용을 후보로 삼는다. 문서 Tool이 대상과 속성을 검증하고 동일 undo/receipt 규칙을 적용할 수 있는 기능만 추가한다.

완료: 검증한 기능은 지원표와 실제 자연어 시나리오에 반영한다. 미지원이면 정확한 사유와 후속 작업으로 남긴다. M10이 보류여도 본문 중심 MVP 결과를 낼 수 있지만 표/서식 지원을 주장하지 않는다.

### M11. 재시작·저장·격리

workspace/폴더/채팅/최근 문서를 재시작으로 복원한다. 접근 권한 재확인과 미저장 복구를 연결한다. 기존 저장 guard와 다운로드 확인을 재사용한다. 업무 전환·저장 실패·중간 종료에서 메시지와 문서 결과가 어긋나지 않게 기록한다.

완료: 원본 폴더 보존, 업무/채팅 격리, 충돌/취소/부분 실패 표시, HWP/HWPX 저장·재열기 및 복구 범위를 확인한다. 원본 파일이 외부 변경됐으면 오래된 결과로 덮어쓰지 않는다.

### M12. 실제 흐름과 인계

아래 수용 검사를 수행하고 결과를 기록한다. 기본 편집기 회귀 검사·타입 검사·빌드와 변경한 런처 API/인증 검사를 수행한다. 최종 소스로 실행 묶음을 만들고 실행 방법, 지원 형식/명령, 실제 provider 검증, 미해결 문제를 문서화한다.

완료: 실제 LLM을 사용한 필수 흐름이 연결되고 검수용 저장물이 준비된다. credentials/endpoint 부재로 실제 호출을 못 하면 부분 완료로 인계한다. 실제 한글 검수는 별도 상태로 남긴다.

| MVP 진행 | 필요한 기본 편집기 작업 | 지금 전부 끝낼 필요가 없는 부분 |

| M03/M11 | E02 열기/저장/닫기, E03 문서 격리, E10 복구의 workspace 연결 | 여러 실행 환경의 동등한 지원 |
| M10 | E05/E06의 검증 가능한 최소 서식/표 | 고급 표·복잡한 스타일 전체 |
| M12 | E12의 빌드·검수 인계, E11의 세 영역 접근성 | E07 전체 개체, E08 고급 쪽, E09 인쇄 확장 |

권장 순서:

1. M00으로 현재 코드/계약을 확인하고 M01~M03의 로컬 업무 화면을 만든다.
2. M04/M08의 engine 연결을 결정적인 fake 응답으로 검증한다. 이 단계의 화면에는 테스트 모드임을 표시한다.
3. M05와 M06/M07을 연결해 선택 자료·실제 provider를 사용한다.
4. M09로 한 번의 사용자 요청을 끝까지 연결한다.
5. M11의 보존·격리·재시작 검증을 통과하고, M10은 작은 capability만 추가한다.
6. M12에서 실제 호출·파일 저장·되돌리기·한글 검수 인계를 묶는다.

한글 미설치 또는 Tauri 빌드 차단은 독립 작업 전체를 멈추는 이유로 삼지 않는다. 엔진 자체를 수정하면 upstream의 새 WASM·독립 기준 검증 지침을 적용하고 기존 npm WASM 검사를 수정 엔진의 검증으로 대체하지 않는다.

## 12. 구현 착수 시 확인할 정보와 산출물

지금 추가 질문 없이 계획에 반영한 기본안은 Rust 런처/Edge·Chrome, IndexedDB와 원위치 폴더 연결, OpenAI 호환 adapter 후보, 세션 메모리 자격증명, 사용자 저장이다.

실제 구현 시작 시 확인할 것은 연결할 provider·endpoint·모델 ID·인증 방식, 기관망 허용 범위, 지원 런타임의 폴더 권한 복원 동작이다. 실제 키는 작업 문서나 Git에 기록하지 않는다. 자료가 없으면 합성 문서를 사용한다.

산출물은 다음과 같다.

- M00~M12 결과와 V01~V28 실행 기록, 실제 지원하는 자료/명령 capability 표.
- workspace/채팅/폴더 저장 구조와 migration, provider 추가 및 Context/loop 확장 위치 안내.
- 실행 가능한 Windows 로컬 묶음, 연결 설정 방법, 실제 모델 검증 범위, 남은 제한.
- 한글에서 확인할 원본·무수정본·AI 적용본·되돌림본과 변경 설명.
- 논리적 단위의 로컬 커밋. 생성물이나 기관 자료·키를 무관한 변경과 함께 stage하지 않는다.

향후 실행 지시문 초안:

> docs/11-workspace-agent-mvp-plan.md의 M00~M12를 구현해줘. 기본 편집기 계획의 필요한 E 작업을 재사용하고, 작업 문서의 우선순위대로 가장 작은 업무·채팅·직접 편집 흐름을 연결해줘. 실제 모델 검증과 mock 검증을 구분하고, 데이터 보존·격리·충돌·부분 실패를 검사해줘. 미지원 기능은 정확히 안내하고 실행 방법·지원 범위·남은 제한·검증 결과를 함께 정리해줘.

이 지시문은 보관용 초안이며 이번 문서 갱신으로 구현이나 예약 실행이 시작되는 것은 아니다.
