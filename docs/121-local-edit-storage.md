# 무관 편집 후 단·표 배치 보존: 합본107

2026-10-18. [파일 작업표](features/05-files-storage-recovery.md) · [직전 합본106](120-native-prefix-storage.md) · [고정 검수 근거](evidence/file-completion-2026-10-18/storage107/README.md).

**뒤쪽 본문·셀을 편집하면 앞쪽 표와 단 경계가 바뀌던 결함을 수정했다.** 공식114에서 Python 예제30경로·150회 저장/재열기와 브라우저7개 검사가 통과했다. 앞서 수정한 MCST32경로도 회귀 통과했다. 이전 버전이 만든 일부 HWPX의 측정 캐시를 거절한 뒤 배치가 달라지는 호환성 결함은 새로 분리해 수정 중이다. 파일 파트 전체 완료를 뜻하지 않는다.

| 원인 | 수정 | 실제 확인 |
| --- | --- | --- |
| 앞 표의 셀 글자를 본문 음수 줄간격의 하한으로 계산 | `painted_flow_text_bottom`에서 표·셀 소유 하위 트리를 제외 | 앞 표28.8px 이동에 따른90개 공개 좌표 변화 해소; 본문 글자 하한은 유지 |
| 문서 어디든 편집됐다는 이유로 변경하지 않은 표의 저장 단 경계를 폐기 | 읽기 시점의 문단 위치·본문/자식 제어 입력·실제 서식 정의·구역 설정을 현재 입력과 비교 | 뒤쪽 편집의175개 변화 해소; 앞쪽 내용·표를 바꾼 반례는 기존 재조판 유지 |
| dirty 표시가 재조판 후 지워진 셀을 미변경으로 오인 | 별도 비직렬화 입력 관측으로 실제 유지된 글자 변경까지 확인 | 이전v6의 host12 retained-text 실패를 보존하고 v7에서 반례 통과 |

새 관측은 원시 바이트·행·원점의 소유권이 아니다. 실제 파서/최초 로드의 두 경계에서만 기록하며, 편집·조회·내보내기·합성 소유권 재봉인은 발급하지 않는다. 위치를 바꾼 문단, 바뀐 서식/쪽/단, 관측 없음, 크기·깊이 한도 초과에서는 기존 경로를 사용한다. 문단당2MiB·깊이64, 구역/컨텍스트 직렬화 예산16MiB를 사용하며 **전체 CPU 시간의 상한을 보장하는 것은 아니다.**

초기 독립 검토에서 문단 위치가 지문에 빠졌고 서식 직렬화가 한도 밖에 있던 문제를 고쳤다. 표 아래의 가짜 캡션 트리만으로 모든 캡션을 검증했다고 해석하지 않는다. 정식8개 반례는 실제 형제 캡션의 **기존 동작 유지**를 확인하며, 캡션 동작 확대를 구현했다고 표시하지 않는다.

복구 최초 실행은 테스트 전용 Edge의 `Browser.crash`가10초 안에 완료되지 않아 실패했다. 조건이나 검사기를 바꾸지 않고 단독 재실행해 실제 강제 종료2회·두 형식 복원·원본 보존·UI 저장을 확인했다. 최초 실패는 근거에 남겼다. 다른29군은 검사기/결과 SHA가 그대로일 때만 재사용했다.

브라우저 이력 검사도 처음 기대를 수정했다. OLE 컨테이너 포장이 달라도 모든 이름 있는 내부 스트림은 정확히 같아야 한다. Redo는 `SnapshotCommand`가 **Undo 직전에** 포착한 상태로 복원하므로, SaveAs가 저장한 커서 위치를 포함한 상태와 비교한다. 현재는 예외 필드 제거 없이 모든 내부 스트림 바이트·원문·실제 지면이 정확히 일치하며, 저장된 커서도 별도 검사한다. 잘못된 초기 기대와 레코드별 분석을 보존했다.
