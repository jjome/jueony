# 새 문서 날짜 초기화와 정확한 시간 값 보존: 합본111

[파일 작업표](features/05-files-storage-recovery.md) · [직전 합본110](123-current-stack-and-preview-storage.md) · [고정 검수 근거](evidence/file-completion-2026-10-18/storage111/README.md).

새 문서가 기본 서식의 과거 작성·수정 시각을 물려받던 결함을 수정했다. 명시적으로 새 문서를 만들 때만 현재 작성·수정 시각과 편집 시간0을 기록한다. 불러오기·복구·다른 이름 저장은 기존 날짜를 바꾸지 않는다. 파일 파트 전체 완료나 자동 저장 시각·편집 시간 누적을 구현한 것으로 표시하지 않는다.

## 실제 동작

| 경계 | 동작 |
| --- | --- |
| 엔진 | 명시적인 정수100ns 값과 원본 지문을 검증하는 날짜 변경 명령, 원본을 바꾸지 않는 사전 검사 |
| 새 문서 | 별도 후보에 날짜·문단 식별자·초기 저장 지문을 준비한 뒤에만 기존 문서와 교체 |
| 실패 | 날짜 초기화 또는 지문 생성 실패 때 기존 문서·이름·파일 연결·세대·이력 유지, 후보만 해제 |
| Agent 새 문서 사전 검사 | 실제 새 사본만 초기화, 활성 문서 불변; 실제 적용·Undo/Redo의 날짜도 검사 |
| 기존 문서 | HWP/HWPX 불러오기·dirty 복구·SaveAs에서 날짜·편집 시간 그대로 보존 |
| 인쇄 시각 | 서식의 원시 값0은 그대로 유지; 비어 있음으로 위장하거나 실제 인쇄를 수행했다고 표시하지 않음 |

엔진은 시계를 읽지 않는다. 앱이 한 번 읽은 밀리초 시각을 `BigInt`로 정확한 FILETIME100ns 정수 문자열로 변환해 전달한다. 입력은4KiB·정규 u64 문자열·중복키·정확한 필드·원본 소유권을 검사한다. 변환할 수 없는 기존 날짜, 잘못된 OLE 속성, 서로 다른 XML/OLE 소유자, 읽기 전용 문서는 임의 복구하지 않는다.

날짜 편집은 기존 OLE 속성과 HWPX 표준 날짜를 동기화한다. 알 수 없는 OLE 속성·바뀌지 않은 raw padding·XML namespace 별칭·모르는 속성과 외부 namespace 내용은 보존한다. 날짜 보존 검사를 제외하거나 좌표 오차를 늘리지 않았다.

공식118은 기존117에서 Rust3파일만 추가·수정했고 다른1,076개 Rust 파일과 물리 배치 지문236개 입력은 그대로다. 날짜 API와 새 문서 앱 연결의 전체 패치·WASM·프런트 지문은 별도로 기록한다.

새 앱 검사의 최초 실패는 검사기가 초기화 중인 iframe에 복구 내보내기를 너무 일찍 요청한 것과 SaveAs 이름 대화상자 확인을 빠뜨린 준비 오류였다. 실제 준비 상태와 이름 확인을 완료하자 **같은 동결 앱**에서12개가 통과했다. 오류를 무시하거나 제품의 보호 조건을 낮추지 않았다. 최초 결과·스택·검사기 원문을 보존한다. 기존 API가 없는117의 날짜14개 실패는 신규 API 부재 대조군이며14개의 별도 제품 결함을 발견했다는 뜻이 아니다.

Native GUI·한글 직접 비교는 사용자 요청에 따라 수행하지 않았다. 새 앱의 복구 검사는 실제 복구 바이트 생성과 dirty 열기이며 신규 crash/IDB 시나리오라고 주장하지 않는다. 기존461개 중 별도 강제 종료·IDB 회귀는 그대로 실행했다.

## 남은 파일 파트

저장 완료를 확인한 뒤 수정 시각을 반영하는 수명, 활성 편집 시간 누적, 저장 취소·부분 실패·Undo·재실행과 독립된 승인 기록은 다음 구현이다. 일반 XSD/XSL·복합 HWT, 미확인 복잡 배치와 전체 한글 동등성도 원래 범위에 남아 있다. 한글 직접 비교 보류를 완료로 바꾸지 않는다.
