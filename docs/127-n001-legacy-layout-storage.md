# N001: 앞 문단 재조판 뒤 HWPX 저장 차단 수정

[기능 작업표](features/05-files-storage-recovery.md#n001) · [고정 검수 증거](evidence/n001-2026-10-18/legacy124/README.md) · [직전 암호화 저장 수정](126-n001-encrypted-layout-storage.md)

**이번에 좁힌 저장 결함은 Rust124에서 수정하고 자동 검증을 마쳤다.** 구버전 HWP의 앞 문단을 편집한 뒤 HWPX 저장을 거절하던 배치 차이와 원본 기록 누락을 해결했다. 다른 기능의 미완성 코드는 실행본에 포함하지 않았다.

| 좁힌 결함 | 구현 | 자동 검증 |
| --- | --- | --- |
| 재조판 문서의 암호화 HWP 저장에서 유효한 행 정보 누락 | 완료: 기존 암호화로 새 유효 기록만 저장·복원 | 기존 WASM7·실제 앱3 재통과 |
| 유효한38바이트 표 속성을42바이트만 인정해 HWPX 배치가 달라짐 | 완료:38/42의 정확한 필드·전체 바이트 일치만 허용 | 두 고정 문서의 편집·양형식·일반/암호 저장, 배치 차이0 |
| 구버전의 해석하지 않은 행 기록이 HWPX 변환에서 누락 | 완료: 원문 바이트를 배치 권한과 분리하여 보관 | 원시 SHA·반복 형식/암호 변경·디스크 재열기·원본 상태 불변 |
| ZIP 인덱스가 중복 항목을 숨겨 충돌을 놓침 | 완료: 일반 파싱·암호 복호화 전에 원시 목록 검증 | 서로 다른 평문 중복·동일한 유효 암호 항목의 중복을 실제 WASM에서 거절 |

이 표의 네 결함 완료가 N001의 원래 전체 범위 완료를 뜻하지는 않는다. **다단·임의 복합 배치·불명확 원점의 일반 지원 확대는 남아 있으므로 N001은 부분 상태를 유지한다.** 한글2024 직접 비교는 사용자 지시대로 보류했다. 이 때문에 전체 작업표를 임의로24/24 또는 한글 호환100%로 바꾸지 않았다.

## 변경 내용

표 속성 검사는 선택 필드가 정확히 없는38바이트와,0으로 있는42바이트만 인정한다. 알려진 필드, 여백, 속성 비트, 빈 설명 및 원시 바이트를 모두 대조한다. 알 수 없는 비트·추가 데이터·다른 길이·비영 값은 계속 거절한다. 오래된 기록을 현재 행 배치 권한으로 승인하지 않는다.

원래 HWP에 해석하지 못한 `/RhwpComputedNativeRowsV1` 스트림이 있으면 같은 형식 저장에서 경로와 바이트를 그대로 유지한다. HWPX에서는 고정된 `META-INF/rhwp-opaque-native-row-stream-v1.bin`에 원시 바이트를 보관한다. 이 수동 보관본을 HWP로 되돌릴 때는 `/RhwpArchivedNativeRowsV1`의 버전·길이·SHA 봉투로 저장한다. 안쪽 바이트는 암호문이어도 해석하거나 현재 배치 권한으로 복원하지 않는다.

각 원문은2MiB로 제한하고 서로 다른 소유자의 충돌, 별칭, 하위 경로, 손상된 봉투와 지원하지 않는 버전을 거절한다. 새 Native 봉투와 고정 HWPX 보관 항목은 암호 저장 시 기존 암호화 경로로 보호한다. 암호·본문이 실제로 검증된 뒤에만 알려진 바깥 봉투를 임시로 해석한다. 새 암호 알고리즘이나 본문 복제 모델을 만들지 않았다.

실제 구버전 입력은 저장소 자체 문서 두 개다. 고정119 엔진의 공개 삽입·저장 API로 다시 만들어 최초 실패 입력과 바이트까지 같음을 확인했다. 양성 검수에서 사설 기록을 지우거나 수정해서 성공시키지 않는다. [입력과 생성 방법](../apps/editor/tests/fixtures/n001-legacy237-own/README.md).

각 행은 서로 다른 실행이며 겹치는 범위가 있으므로 독립 검증 수로 합산하지 않는다. 실제 앱 검사에서는 일반/암호 열기, 앞 문단 편집, 암호 설정, 다른 이름 저장, 후속 저장, Undo/Redo, 저장 결과 재열기를 수행한다. 실제 OPFS 바이트와 별도 Node 디스크 재읽기를 대조한다. 사용자 창·문서는 사용하지 않았다.

보존 비교는 기존 의미 전체, 공개 지면 전체, 좌표 허용오차0.2와 기존 한도를 그대로 쓴다. 원본 기록의 정확한 SHA 검사는 여기에 추가했다. 최초 실패와 검사 준비 오류도 증거의 `before/`에 남겼다. 특히 원시 ZIP의 중복 허용 실패는 검사 기대값을 바꾸지 않고 Rust 파서에서 수정했다.

## 소스와 실행

공식 엔진 소스는 `587008f751f4f6dc`, 패치124개, WASM SHA256은 `059042712aea0db19beb8383d3aee53db0dfd0a2c134c378d256ef665263e1ed`다. 배치 자원 지문은248개 실제 입력을 사용하며 기존243개를 모두 유지한다. 이전 엔진과 비교한 런타임 입력1,392개 중 N001 관련11개만 다르고 나머지1,381개는 같다.

앱은 커밋 `b0f349c3`의 고정 소스에서 빌드했다. 작업트리에 남아 있는 저장 시각 수명·최근 문서 Agent 변경은 보존하되 이 실행본에서는 제외했다. 이번 문서 처리 수정은 Rust이며 Python은 검수 실행과 증거 정리에 사용했다.

저장소 상단의 **`Start-Jueony-FileReview.cmd`**로 새 N001 검수 실행본을 연다. 전용 포트는4390이고 실행 묶음은 `build/n001-clean-review123/build/jueony-n001-review124`에 있다. 기존 실행본과 서버를 종료하거나 덮어쓰지 않았다. 별도 origin이므로 기존 업무 상태를 자동으로 이동하지 않는다.

이 보관 규약은 Jueony의 사설 부가 항목이다. 모든 미해석 CFB/XML 기록의 일반 변환 보존이나 외부 한글이 사설 항목을 재저장까지 유지한다는 보장은 검수하지 않았다. 한글의 실제 화면·인쇄·재저장 비교와 원래 N001의 범위 밖 배치는 후속 검수·구현 대상이다.
