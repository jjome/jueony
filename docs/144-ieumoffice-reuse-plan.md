# 144 Jueony 개발을 위한 이음오피스 활용 계획

작성일 2026-11-20. Jueony 개발을 계속하면서 이음오피스의 독립 모듈, 편집 도구, 실패 처리와 검증 사례를 활용한다. 첫 적용 순서는 **행정 문서 검사 → 자료 검색 → Agent 반복 실행 → 표와 쪽 배치 진단**이다.

**2026-11-21 갱신:** 비교 계획 커밋 `a72a96a8`을 `main`에 반영했다. 아래 [구현 착수 계획](#implementation-start)의 실행 환경 복원과 단계별 산출물을 현재 개발 순서로 사용한다. 이번 변경은 계획 통합이며 이음오피스 코드 이식이나 제품 기능 완료를 뜻하지 않는다.

## 개발 방향과 기준

Jueony의 업무별 다중 폴더, 채팅별 자료 선택, 문서 명령 계약과 저장 보존 정책을 제품의 기준으로 둔다. 이음오피스에서 이미 해결한 기능은 해당 코드의 의존성과 입력·출력 계약을 확인해 필요한 단위로 가져온다. 같은 기능을 처음부터 다시 설계하는 작업을 줄이는 것이 목적이다.

이음오피스 기준은 [v0.13.0 릴리스](https://github.com/pblsketch/ieumoffice/releases/tag/v0.13.0), 커밋 `8602a39410adb86037f3008588b64efc75b08c60`다. 한글 엔진은 [rhwp 0.9.0 기반 0.9.0-ieum.33](https://github.com/pblsketch/ieumoffice/blob/8602a39410adb86037f3008588b64efc75b08c60/vendor/rhwp-core/package.json)이다. Jueony 비교 기준은 로컬 `main`의 `881d9ec5b46201fc60258651a13743c7e3b5cafe`와 분석 당시 작업 폴더다. 후속 구현을 시작할 때 실제 통합 HEAD, 적용 엔진과 미커밋 변경을 다시 기록한다.

이음오피스 v0.13.0에는 머리말·꼬리말, 다단, 수식과 중첩 표의 AI 도구가 있다. 이전 v0.12.12 비교에서 확인한 제한을 최신판의 기능 부재로 해석하지 않는다. 도구별 세부 제한은 [한글 AI 도구 계약](https://github.com/pblsketch/ieumoffice/blob/8602a39410adb86037f3008588b64efc75b08c60/apps/hwp/src/renderer/ai/hwp-skill.ts)과 실행 코드로 확인한다.

기능과 의존성은 소스로 대조했다. 이 계획의 절감 효과와 이식 난도는 정성 판단이며, v0.13.0의 실제 이식 공수와 기관 환경에서의 동작은 첫 적용에서 측정한다. 2026-11-10에 수행한 v0.12.12 엔진의 10개 파일 재열기 결과는 해당 버전의 참고 기록으로 취급한다.

## 의존성과 이식 경계

- **행정 문서 검사**의 `packages/doc-rules`는 외부 런타임 의존성이 없는 순수 검사 모듈이다. 규칙 데이터와 검사 함수를 재사용하고, 문서 구조·원문 위치를 읽는 어댑터를 Jueony에 둔다. 규칙별 적용 범위와 비활성 기본값을 유지한다. 검사 통과는 전체 행정 문서 규정 준수 판정과 구분한다.
- **자료 검색**은 한국어 토큰화·순위 계산을 먼저 적용한다. FTS5 상시 색인을 도입할 때는 현재 Node 호스트의 SQLite 지원과 실제 배포 런타임을 확인한다. 검색 범위는 업무·채팅·선택 자료의 권한으로 제한한다.
- **Agent 실행**의 핵심 loop는 외부 의존성이 적지만 도구·메시지·취소 계약은 우리 모델 Port와 다르다. 이음오피스의 기본 최대 100턴을 그대로 적용하지 않고, 첫 시험에서 호출 횟수·시간·입력 크기와 반복 오류 한도를 명시한다. 실제 문서 변경은 우리 revision·대상 검증·receipt·undo를 거친다.
- **자료 추출**의 `file-parse` 전체는 여러 문서 엔진에 의존한다. PDF·DOCX 등 필요한 형식을 먼저 선택하고, 추출 누락·암호·OCR·표 구조 제한을 결과에 포함한다.
- **인쇄**의 `print-layout/plan`은 Node·Electron·PDF 라이브러리를 가져오지 않는 배치 계산 진입점이다. 전체 PDF 재배치에는 PDFium·pdf-lib 의존성이 있다. 순수 계산과 호스트 출력 연결을 나누어 검토한다.
- **한글 편집 UI**와 공통 작업 카드는 React 기반이다. Jueony의 DOM 기반 shell에는 상태 모델·조작 흐름·검증 사례를 우선 적용한다. UI 하나를 가져오기 위한 전체 프레임워크 전환은 별도 비용으로 평가한다.
- **엔진 패치**는 rhwp 0.8.7과 0.9.0의 내부 구조·API 차이를 먼저 대조한다. 특정 패치의 이식과 엔진 버전 업그레이드를 별도 작업으로 관리하고, 우리 보존 검사와 기존 복합 문서 회귀를 통과시킨다.
- **workspace 패키지**의 `private: true`는 npm 공개 패키지가 아니라는 뜻이다. 소스·필수 파일·전이 의존성·라이선스를 함께 추적한다. 가져올 코드의 실제 범위를 고정한 뒤 우리 모듈 경계에 연결한다.

### 검색 채택 기준

기존 [평가 기록](evidence/rag-evaluation-2026-10-13/report.md)은 21개 파일·22개 질문에서 source recall@1 27.8%, recall@3 83.3%, recall@8 100%, MRR 0.567이며 무답 질문 4개 중 3개에 검색 결과를 반환했다. 이는 과거 추출·검색 기록이며 이번 환경에서 재실행한 결과나 모델 답변 정확도가 아니다.

1. 먼저 기존 평가기와 manifest가 요구하는 고정 엔진 해시를 재현한다. 최신 엔진 결과는 별도 출력 폴더에 기록하고, 기존 증거·정답을 덮어쓰거나 새 엔진을 과거 manifest에 억지로 맞추지 않는다.
2. 같은 파일·질문·scope·추출 텍스트로 기존 검색과 후보를 비교한다. top-1과 MRR 개선, recall@8 비하락, 무답 오탐 감소를 채택 조건으로 둔다. 변경·삭제·미선택 자료 노출은 0건이어야 한다.
3. 최신본을 무조건 우선하지 않고 질문의 기준일·요청 버전·근거 권위를 구분한다. 무답 판별은 겹치는 단어만 있는 질문을 포함해 평가한다.
4. 지연·색인 시간·디스크 사용량과 재실행 결과도 함께 기록한다. 개선이 입증되기 전 기본 검색을 교체하지 않으며 임베딩·hybrid는 별도 비교 후보로 남긴다.

### Agent 실행 예산과 검수 범위

첫 실험 상한은 **모델 4회, 읽기 도구 8회, 총 180초, 누적 직렬화 입력 1,500,000자, 최종 편집 1회**로 고정한다. 현재 bounded의 2~3회·120초 기본값은 유지하며 새 loop 설정과 분리한다. 같은 도구·인자·문서 revision 호출을 반복하거나 도구 오류가 2회 연속 발생하면 중단하고 이유를 표시한다. 예산 초과·취소·권한/대상 불일치·사용자 편집 후에는 후속 편집을 적용하지 않는다.

`ModelGatewayPort.generate()`는 현재 검증 전 편집 후보를 반환하는 계약이다. 여기에 도구 응답을 암묵적으로 섞지 않고 새 요청/결과 타입과 provider별 mapping을 먼저 설계한다. 읽기 도구는 처음에는 현재 문서 조회와 선택 자료 찾기로 제한하고, 파일 쓰기·표 구조 변경은 첫 loop에서 노출하지 않는다. UI의 완료 표시는 실제 receipt와 검증된 진단 범위를 따른다.

모의 공급자 검사는 프로토콜·취소·오류 보호의 증거다. 실제 모델의 재계획·답변 품질은 같은 평가 세트에서 single/bounded와 성공률·근거·지연·호출량을 별도 비교한다. 실제 모델 검증 전에는 그 제공자의 loop를 지원 완료로 표시하지 않는다.

IU00 이후 IU01 → IU02 → IU03 → IU04 순서로 첫 적용을 진행한다. 각 단계는 영향받는 공개 계약을 먼저 정하고 소비자와 함께 검증한다. IU05와 IU06의 개별 착수는 확인한 효과·의존성·필수 업무 요구에 따라 정한다.

검색은 개선 효과를 평가한 뒤 채택한다. Agent는 작은 도구 집합이 안정화된 뒤 표·파일 명령으로 확장한다. 저장과 복구는 모든 단계의 회귀 조건으로 확인한다.

## 변경 관리와 검증 기록

각 이식은 선택한 소스 단위와 테스트를 함께 검토 가능한 크기로 커밋한다. 원본 기능을 그대로 가져온 부분, 우리 구조에 맞춰 바꾼 부분, 지원에서 제외한 부분을 변경 설명에 기록한다.

문서 변경은 제공자 중립 명령 schema, 대상·revision 검사, 사전 검사, 실제 실행, receipt, 요청 undo와 저장 검증을 따른다. 원본 파일 접근은 기존 파일 연결·권한 계약을 사용한다. 검색·첨부·Agent 도구는 업무와 채팅의 자료 범위를 확인한다. 취소나 전환 뒤 도착한 응답이 새 문서에 적용되지 않도록 회귀 검사를 둔다.

이식 기록에는 아래 정보를 남긴다.

- upstream 저장소, 고정 커밋, 원본 파일과 패치 해시, 실제 재사용 범위
- 변경한 우리 파일, 공개 계약과 적용 엔진·배포 런타임의 영향
- 기존 테스트 중 재사용한 사례와 새로 발견한 회귀, 실행 명령과 결과
- 실제 모델·독립 한글·기관망 검증의 적용 범위와 남은 제한
- 전이 의존성, 실행 묶음 크기와 필요한 라이선스 고지

상태 원본은 [전체 작업 CSV](jueony-work-checklist.csv)다. 구현·검증·Agent 연결을 각각 완료조건에 따라 갱신한다. 순수 규칙·격리·오류 처리는 해당 자동 검사로 검증하고, HWP 조판·저장 의미가 바뀌는 작업은 실제 한글 검수가 필요한 범위를 함께 기록한다. [완료 규칙](97-master-work-checklist.md)을 따른다.
