# Jueony 후속 개발 작업 계획

2026-10-11. **한글 2024의 기능·동작을 먼저 전수 점검하고, 문서 및 환경 상태의 저장·복원을 맞춘 뒤 Agent를 결합한다.** 사용자가 한글에서 익힌 작업을 그대로 이어가는 편집 경험이 제품의 출발점이다. 이번 변경은 작업 문서이며 기능 구현 완료 보고가 아니다.

최우선 상세 작업은 [한글 기능 동작 및 상태 저장 점검](25-hangul-parity-and-state-plan.md)이다. 메뉴 모양뿐 아니라 선택·포커스·단축키·기본값·확인/취소·undo·저장·재실행 결과를 같은 기준으로 비교한다. 사용자 조작·단축키·AI·매크로는 같은 문서 명령과 상태를 사용한다.

## 최우선 선행 작업

1. 한글 2024의 전체 메뉴·대화상자·문맥별 동작·단축키를 기준으로 현재 구현/부분 구현/미구현/미검증을 전수 대조한다.
2. 문서 고유값, 새 문서 기본값, 사용자 환경, 문서별 보기, 작업 session과 복구의 저장·복원 수명을 실제 한글과 비교하고 보강한다.
3. 입력·기본 편집·저장/복구·설정 유실 등의 기반 차이를 우선 수정하고 실제 한글 저장물 검수를 수행한다.
4. 그 기반 위에서 한 화면의 UI와 Agent를 통합하고 브라우저 연결·RAG·loop·추가 AI 기능·매크로를 진행한다.

새 기능보다 위 순서가 우선한다. 기존 동작과 엔진·설정 서비스를 재사용하며, 아래 6개 확장 요구사항도 유지한다.

## 1 브라우저 로그인으로 AI 계정 연결

사용자가 2026-10-11 확정한 요구사항은 **브라우저 로그인·인증 링크로 AI 계정을 연결하는 것**이다. 연결 버튼→기본 브라우저에서 제공자 로그인과 권한 동의→Jueony 복귀→계정·모델 선택 흐름으로 구현한다. CLI 설치·실행이나 MCP URL 추가를 이 요구사항의 완료로 계산하지 않는다.

### 사용자 흐름

1. AI 연결 설정에서 제공자와 **브라우저로 연결**을 선택한다. 해당 방식이 검증되지 않은 제공자에는 지원되는 API 키 방식과 상태를 안내한다.
2. 기본 브라우저에서 공식 로그인 페이지를 연다. 자동 열기가 실패하면 동일한 인증 링크 복사와 취소를 제공한다. 비밀번호 입력·추가 인증은 제공자 화면에서 수행한다.
3. 인증 완료 후 앱에 연결 계정과 사용 경로를 표시한다. 브라우저 복귀만으로 모델 호출까지 성공했다고 표시하지 않는다.
4. 사용할 모델을 고르고 합성 연결 검사로 실제 추론 권한을 확인한다. 로그인 성공·모델 사용 가능·연결 실패를 구분한다.
5. 이후 저장된 연결을 선택해 사용한다. 만료 시 갱신 또는 재연결을 안내하며 계정 전환·연결 해제를 제공한다.

### 제공자별 출발점

2026-10-11 공식 문서에서 확인한 지원 경로이며, Jueony의 브라우저 인증은 아직 구현·실호출 검증 전이다. 로그인 권한과 모델 호출 권한, 구독 사용량과 API 과금을 구분한다.

| 제공자 | 확인한 공식 경로 | Jueony에 적용할 작업과 조건 |
|---|---|---|
| GPT / ChatGPT | Sign in with ChatGPT는 계정 식별과 선택적인 ChatGPT plan usage를 구분한다. 현재 가이드는 오픈소스·개인 로컬 프로젝트·선정된 비공개 앱 등 적용 대상을 명시한다. | 현재 개인 로컬 개발판의 적용 자격·등록·추론 scope를 먼저 검증한다. 기관 배포/유료 제품은 별도로 자격을 확인한다. 기존 GPT API 키 연결은 유지한다. |
| Gemini | Gemini API OAuth 가이드는 Google Cloud 프로젝트·동의 화면·Desktop app OAuth client와 사용자 인증 절차를 제공한다. | 앱 등록·scope·프로젝트 사용 권한과 모델 호출을 검증한다. Google 로그인만으로 Gemini 소비자 구독이 API 사용량을 제공한다고 표시하지 않는다. |
| Claude | 제3자 제품에 Claude.ai 직접 로그인을 제공하거나 구독 토큰을 자체 호출에 사용하는 방식은 공식 안내에서 제한한다. 수정하지 않은 공식 Claude Code 실행은 별도의 조건을 둔다. | 현재 검증된 API 키 연결을 유지한다. 별도 허용된 직접 연동이 확보되기 전에는 자체 Claude 구독 로그인 버튼을 지원 완료로 노출하지 않는다. 공식 CLI 연동은 다른 실행 구조를 요구하므로 독립 검토 과제다. |
| HyperCLOVA X | 확인한 CLOVA Studio API 안내는 API 키 발급·헤더 인증 방식이다. | 현재 API 키와 기관 endpoint를 유지한다. 일반 NAVER 로그인만으로 모델 호출 권한이 생긴다고 가정하지 않는다. 기관 SSO/gateway 또는 공식 OAuth 제공 여부는 별도 확인한다. |

근거: [OpenAI 연결 개요](https://developers.openai.com/siwc/quickstart), [개인 로컬 프로젝트와 배포 조건](https://developers.openai.com/cookbook/articles/sign-in-with-chatgpt), [Gemini OAuth](https://ai.google.dev/gemini-api/docs/oauth), [Claude 제품 내 실행과 인증 조건](https://code.claude.com/docs/en/legal-and-compliance), [CLOVA Studio API 키](https://guide.ncloud-docs.com/docs/clovastudio-apikey).

현재 [Jueony 이용허락](../LICENSE.txt)은 개인·비업무용 맞춤 약관이므로, 저장소가 공개되어 있다는 이유만으로 오픈소스 대상 인증 경로의 자격을 충족한다고 간주하지 않는다. 개인 로컬 검증과 타인에게 배포할 제품의 조건을 각각 확인하며 인증 기능을 위해 라이선스를 임의로 변경하지 않는다.

### 구현 작업

- 인증 책임을 `AuthProvider` 경계로 분리한다. 연결 설정에는 인증 방식·계정·만료 상태와 모델 설정을 구분하고, LLM Port는 제공자별 로그인 절차를 알지 않게 한다.
- 제공자가 공식 지원하는 PKCE/state·callback 검증 또는 device flow를 구현한다. issuer·redirect·scope·client 등록 조건을 확인하고 다른 제품의 client ID나 저장 토큰을 가져오지 않는다.
- `연결 중 / 로그인 완료 / 모델 사용 확인 / 취소 / 만료 / 권한 부족 / 연결 해제`를 구분한다. 인증 요청의 수명·중복 callback·앱 종료 후 남은 요청도 처리한다.
- 사용자 비밀번호는 Jueony에서 받지 않는다. 토큰은 로컬 호스트의 보호 저장소에서 관리하고 채팅·일반 로그·편집기 iframe에 전달하지 않는다. 평문 저장 fallback은 두지 않는다.
- 계정 재연결 시 기존 연결과 새 연결을 구분하고, 의도하지 않은 계정 덮어쓰기나 다른 업무의 모델 자동 전환을 방지한다. 제공자가 지원하는 revoke와 로컬 연결 삭제를 구분해 처리한다.
- 연결 검사에서는 사용자 문서·자료·채팅을 전송하지 않는다. 계정 식별만 허용된 토큰으로 추론을 시도하지 않으며 모델별 실제 권한을 검사한다.
- 사용 중인 연결이 구독 사용량인지 API 과금인지 표시한다. 연결 실패를 다른 유료 연결로 자동 전환하지 않는다.
- 폐쇄망에서는 외부 브라우저 로그인을 필수로 요구하지 않는다. 허용된 기관 인증·endpoint와 기존 로컬 편집을 유지한다.

완료 기준: 공식 지원 경로 하나에서 브라우저 로그인→앱 복귀→모델 선택→합성 호출→실제 문서 편집을 완주한다. 성공·취소·만료·갱신·재실행 복원·계정 전환·해제를 검사하고, 나머지 제공자는 실제 검증 상태로 표시한다. 인증만 성공한 상태와 모델 호출까지 검증한 상태를 혼동하지 않는다.

OpenCode/Claude Code는 로그인 UX의 참고 대상이다. 외부 CLI 실행 backend나 MCP client/server는 별도 확장 과제로 유지하며 이번 브라우저 로그인 요구사항에 자동으로 포함하지 않는다. [OpenCode 제공자 연결](https://docs.opencode.ai/docs/providers/), [Claude 로그인](https://code.claude.com/docs/en/authentication).

## 2 업무 화면과 문서 편집기를 하나로 통합

목표 화면은 하나의 상단 메뉴·도구 모음, 왼쪽 업무/대화/자료, 가운데 대화, 오른쪽 문서다. 문서 집중 모드에서는 업무·대화를 접고 편집 영역을 넓힌다. 단축키와 문서 도구는 한글 2024의 익숙한 위치와 동작을 유지한다.

작업:

- `shell.*`, `chrome-2024.ts`, 편집기 toolbar의 버튼·제목·저장 상태를 대조해 소유 화면을 정한다. 열기/새 문서/저장/되돌리기의 중복 진입점과 서로 다른 상태 표시를 정리한다.
- 색상·글꼴·아이콘·간격·입력창·대화상자 규칙을 공통 스타일로 정의하고 양쪽 화면에 적용한다.
- 먼저 iframe 안의 중복 chrome을 줄이고 host에 필요한 명령·선택·서식·dirty 상태를 전달한다. 렌더러·IME·undo를 유지한 채 화면 통합을 검증한다. iframe 제거 자체를 완료 조건으로 삼지 않는다.
- 상단 도구 모음은 활성 문서와 선택 상태를 따른다. 적용할 문서·표·셀을 이름과 상태로 확인할 수 있게 한다.
- 왼쪽 대화/폴더 높이, 대화/문서 너비, 패널 접기, 마지막 배치를 복원한다. 좁은 화면에서는 메뉴를 접고 문서 확대율을 사용자가 조절한다.
- Ctrl+S는 활성 문서 저장으로 연결하고, 편집 명령은 문서 선택·포커스에 맞게 전달한다. 채팅 입력의 Ctrl+Z, IME 조합, 입력창 단축키는 문서 명령과 충돌하지 않게 한다.
- 지원하지 않는 기능은 비활성 이유를 표시하고, 실행할 수 있는 메뉴와 구분한다.

완료 기준: 1366×768/1920×1080, Windows 배율 100%/125%/150%에서 주요 버튼 접근 가능. 마우스 없이 문서↔대화 이동, 한글 입력, 표 선택, 기존 한글 단축키, 저장·탭 전환·undo 회귀 검사를 통과한다. 픽셀 모양만 같아도 동작과 상태가 이중으로 나뉘면 완료가 아니다.

## 3 RAG와 제한된 Agent loop

기존 [Agent 확장 설계](22-agent-retrieval-execution-design.md)를 구현 기준으로 삼는다. RAG는 필요한 자료를 찾는 책임, loop는 결과를 보고 다음 행동을 결정하는 책임이다. 먼저 검색·도구 실행을 계측하고 기존 single 실행과 비교한다.

작업 순서:

1. **근거와 평가 기준**: 문단·표/셀의 출처 위치와 파일 버전을 보존한다. 공문·계획서·예산표·보고서의 정답 문서/질문을 만들고 현재 single 결과를 기록한다.
2. **로컬 검색**: 업무/공통/임시 자료 범위를 분리한 구조 추출과 키워드 검색을 만든다. 폴더 연결·색인 중·완료·오류를 구분하고 변경/삭제/연결 해제 시 결과를 갱신한다.
3. **실행 journal과 사전 검증**: 작업별 명령·결과·revision·취소·실패를 기록하고 편집기 사본에서 계획을 검사한다. 중복 적용과 부분 실패를 구분한다.
4. **bounded loop**: 자료 찾기→원문 읽기→문서 확인→편집 계획→검사→완료를 예산 안에서 수행한다. 초기 제안 한도는 모델 4회, 읽기 도구 8회, 총 180초, 최종 문서 적용 1회다.
5. **검색 품질 추가 실험**: 키워드 검색에서 부족한 사례가 확인되면 로컬 임베딩·hybrid 검색·reranker를 비교한다. 벡터 검색 준비를 첫 loop의 필수 조건으로 삼지 않는다.

항상 유지할 조건:

- 사용자 미저장 내용을 포함한 현재 문서가 기준이다. 사용자 편집·업무 전환·문서 전환 후 오래된 결과를 덮어쓰지 않는다.
- 진행 화면은 수행 단계·결과·중지·예산을 보여준다. 실제 변경은 실행 receipt로 판정한다.
- 모델 생성문이나 참고 파일의 문장은 사용자 지시·도구 권한으로 승격하지 않는다.
- loop 실패·취소 시 사용자 편집은 유지한다. 성공한 AI 변경은 요청 단위 undo로 복원한다.
- 다른 업무 자료 포함, 삭제된 자료 재사용, 중복 적용, 사용자 변경 유실은 모두 실패로 판정한다.

완료 기준: 같은 평가 세트에서 single 대비 성공률·근거 정확도·지연·비용을 비교한다. 정답 근거가 없을 때는 부족함을 표시한다. 품질 개선이 확인된 요청 종류에만 loop를 기본 사용한다. 상세 목표 수치는 22번 문서의 평가 관문을 따른다.

## 4 한글 기능을 Agent 도구로 확대

최종 목표는 한글 2024에서 사용하는 문서 작업을 Agent가 수행하는 것이다. 기능 이름이 메뉴에 있다는 이유만으로 AI 지원으로 표시하지 않는다. 현재 [68행 기능표](ai-editor-capability-matrix.csv)를 출발점으로 한글 2024 메뉴·대화상자·단축키와 기관 대표 문서를 대조해 누락 기능을 추가한다.

| 확장 묶음 | 주요 작업 |
|---|---|
| 본문과 서식 | 문단 삽입·삭제·이동, 부분 범위와 혼합 서식 보존, 글자/문단 모양, 스타일 생성·수정·적용, 번호·글머리·탭 |
| 표 | 병합/분할, 다중 문단·중첩, 행/열과 셀 크기, 테두리·채우기·정렬, 제목 행, 쪽 넘김, 계산 |
| 쪽과 구역 | 구역 추가·삭제, 다단·나누기, 머리말/꼬리말, 쪽 번호, 쪽 테두리·배경·바탕쪽 |
| 개체 | 그림·도형·글상자·수식의 생성·조회·수정·삭제, 위치·감싸기·크기·회전·그룹·캡션 |
| 필드와 검토 | 누름틀·양식, 책갈피·링크·각주/미주, 차례·상호 참조, 메모·변경 추적·문서 비교 |
| 파일과 출력 | 새 문서·열기·저장·다른 이름 저장, 내보내기·인쇄, 복구·보호 상태, 원본 형식 보존 |

각 기능은 `현재 엔진 가능 / 엔진 확장 필요 / 보존만 가능 / 미지원`을 구분한다. 보기·선택 기능은 파일 직렬화 검사를 적용하지 않는 등 기능별 검수 범위를 지정한다. 모든 작업을 Rust로 재작성하지 않고 기존 Rust/WASM 문서 엔진과 TS 명령 계층을 재사용한다.

공통 완료 조건:

1. 읽기 가능한 대상·속성·제약과 매개변수를 정의한다. 기능별 사용 가능 여부와 거절 이유를 조회할 수 있어야 한다.
2. UI·단축키·AI가 동일한 명령 구현을 호출한다. 대화상자 열기와 실제 문서 변경은 다른 단계로 분리한다.
3. 대상·원문·revision·인자 검증, 성공 결과와 오류 코드를 구현한다.
4. 여러 명령 묶음의 실패 복원·undo/redo·사용자 편집 충돌을 검사한다.
5. 문서 변경 기능은 HWP/HWPX 저장·엔진 재열기와 실제 한글 대표 표본 검수를 수행한다.
6. 통과한 범위만 Agent capability 목록에 노출한다. 엔진이 보존하지 못하는 구조는 명시하고 조용히 제거하지 않는다.

내부 공통 명령 서비스가 먼저다. 외부 Claude Code/OpenCode 등이 열린 문서를 조작하도록 이 서비스를 표준 도구로 공개할 때 별도 **MCP server adapter**가 된다. MCP 자체가 빠진 엔진 기능을 구현해 주지는 않는다.

## 5 공무원 업무 흐름

기관·부서별 양식과 작성 관행을 선택 가능한 업무 프로필로 만든다. 제품 문구는 “업무”, “자료”, “작업 대화”, “반복 작업”처럼 사용자에게 익숙하게 제공하고 내부의 RAG/loop 용어는 설정·진단에 한정한다.

첫 업무 시나리오:

| 업무 | 입력과 동작 | 검수 |
|---|---|---|
| 전년도 계획을 올해 계획으로 | 지난해 문서 + 올해 변경점 → 항목 대응·초안·일정표 | 그대로 유지할 수치와 변경할 수치, 근거, 빠진 입력 구분 |
| 공문 초안 | 사용자 지정 기관 양식 + 목적·대상·기한·붙임 → 초안 | 수신·제목·본문 항목·붙임 누락과 양식 보존 |
| 결과 보고 | 계획·실적 자료 → 추진 실적·차이·향후 조치 | 실적 근거, 기간, 숫자/합계 검증 |
| 예산/일정 표 정리 | 지정 표·자료 → 표 작성/수정 | 단위·합계·날짜, 미확정 값을 임의 확정하지 않음 |
| 반복 서식 정리 | 선택한 양식 정책 → 제목·본문·표 서식 일괄 적용 | 다른 내용 보존, 적용 범위 표시, 한 번에 undo |

작업: 템플릿 등록/버전 관리, 기관 용어·약칭·문체 설정, 필수 입력 안내, 근거 클릭, 숫자·날짜·붙임 검사, 실제 공무원 사용성 검수표. 공문 형식을 전국 공통의 단일 규칙으로 하드코딩하지 않는다. 기관 내부 정책·전송 허용 endpoint·보관 기간은 업무 프로필과 관리자 정책에 반영한다.

완료 기준: 위 5개 시나리오를 자료 선택부터 문서 저장까지 수행하고 공무원 검수자가 수정 필요 항목을 기록할 수 있다. 근거 없는 사실·발신 권한·결재 완료를 만들어 표시하지 않는다. 전자결재 제출·메일 발송·행정 시스템 연계는 별도 외부 연동 범위다.

## 6 반복 작업 매크로

반복 작업은 두 종류로 구분한다.

- **명령 매크로**: 확정된 문서 명령과 매개변수를 저장한다. 재실행 때 모델을 호출하지 않아 같은 입력/엔진/설정에서 결과를 재현할 수 있다.
- **AI 작업 템플릿**: “이번 달 실적 보고 초안”처럼 요청·자료 선택 규칙·양식·검사 항목을 저장한다. 실행마다 모델 응답을 새로 검증하고 사용량과 결과가 달라질 수 있음을 표시한다.

초기 범위는 제목/본문 서식 통일, 지정 값 교체, 표 서식 정리의 3개 명령 매크로와 월간 보고 초안 1개 작업 템플릿이다. 문서 제어가 검증된 기능부터 제공한다.

작업:

- 매크로 만들기·명명·편집·복제·삭제·내보내기·가져오기, 한글 2024 매핑과 충돌하지 않는 실행 단축키.
- 공통 명령 계층에서 성공한 의미 단위 작업을 기록한다. 마우스 좌표·키 입력·대화상자 클릭 자체를 재생하지 않는다. 초기에는 기록 가능한 명령만 표시한다.
- 기록본에서 문서별 임시 ID를 그대로 재사용하지 않는다. 제목/북마크/양식 필드/조건식 등 목표 규칙과 예상 개수를 저장하고, 실행할 문서의 revision에서 대상을 다시 해석한다.
- 날짜·연도·사업명·부서·금액 등을 매개변수로 바꾼다. 찾은 대상이 없거나 여러 개로 모호하면 실행 전에 구체적으로 알린다.
- 시험 실행으로 변경 예정 범위와 작업 목록을 확인하고, 실제 실행은 한 묶음으로 기록·undo한다. 원본 템플릿을 덮어쓰는 저장은 출력 규칙에서 구분한다.
- 매크로 정의에 schema/engine 버전과 필요한 capability를 남긴다. 미지원 명령·버전 변경·보호 문서·예산 초과·실패 중단을 처리한다.
- 기존 문서에 들어 있는 한글 스크립트 매크로 실행/호환은 별도 과제다. Jueony 명령 매크로와 동일한 형식이라고 가정하지 않는다.

완료 기준: 같은 반복 작업을 서로 다른 3개 표본에서 매개변수를 바꿔 실행하고 예상 대상만 변경한다. 중간 실패·대상 모호·사용자 동시 편집에서 잘못된 부분 적용이 없어야 한다. 저장 후 HWP/HWPX 재열기와 요청 전체 undo를 확인한다.

## 공통 구조

```text
통합 UI / 한글 단축키 / Agent / 매크로 / 외부 MCP
                ↓
명령 서비스: capability · 대상 해석 · 인자/revision 검증 · 실행 · receipt/undo
                ↓
현재 문서 session → 기존 Rust/WASM 엔진 → 동일한 저장 서비스

Agent 실행 제어 → Context 공급(현재 문서 / 지정 자료 / RAG)
               → LLM Port → 제공자 adapter
연결 설정 → AuthProvider → 제공자 브라우저 인증 → 보호 저장소와 연결 상태
```

UI 위젯·LLM 응답·매크로 단계는 위 명령 계약으로 변환한다. 검색 엔진이나 모델 adapter가 편집 중 파일을 별도로 쓰지 않는다. 매크로가 다른 실행 경로로 편집 검증을 우회하지 않는다.

## 구현 순서와 완료 산출물

아래 표는 우선순위다. 실제 병렬 배정과 선행 의존성·통합 관문은 [병렬 작업 순서](26-parallel-execution-plan.md)를 따른다. 통합 담당 1명과 A/B/C 3개 작업을 기본으로 하고, H00 후 기능·상태·엔진 조사를 병렬 수행한다. 기반 검증 뒤에는 브라우저 인증·로컬 검색·AI 도구를 병렬 진행하고, 필요한 계약이 통과하면 loop와 매크로를 병렬 개발한다.

| 순서 | 작업 ID | 작업 묶음 | 다음 단계에 넘길 결과 |
|---|---|---|---|
| 0 | H00~H01 | 한글 기준 고정과 기능·동작 전수 점검 | 한글 목록→Jueony 명령/엔진/실행 비교 매핑, 구현·미구현·차이·미검증 보고 |
| 1 | H02 | 상태 저장·복원 동작 대조 | 문서/새 문서 기본값/환경/보기/session/복구별 소유 범위·저장 수명·전이 검사 |
| 2 | H03~H04 | 기본 편집·상태 차이 수정과 독립 검수 | 입력·단축키·저장·재실행의 기반 결함 수정, HWP/HWPX와 실제 한글 검수 |
| 3 | H05/P01 | 같은 편집기의 UI와 공통 명령 통합 | 한글 사용 흐름 유지, 단일 chrome·상태·저장, Agent를 접어도 완결된 수동 편집 |
| 4 | P02 | 브라우저 계정 연결 | 공식 지원 제공자의 인증→앱 복귀→모델 선택→문서 편집. 제공자 자격 확인 포함 |
| 5 | P03 | 출처·로컬 검색 RAG | 업무 격리·근거 이동·변경/삭제/해제 갱신, 현재 single 기준과 비교 |
| 6 | P04 | journal·staging·bounded loop | 한도·중지·충돌·실패 복원·단일 적용·전체 undo, single 대비 평가 |
| 7 | P05/P07 | 한글 기능의 AI 제어와 공무원 업무 양식 확대 | H01 기능표와 연결해 고급 표·개체·필드·쪽·출력별 명령·파일 보존·한글 검수 |
| 8 | P06 | 명령 매크로와 AI 작업 템플릿 | 변수·대상 규칙·시험 실행·전체 undo와 실제 한글 매크로 동작 차이 기록 |

한글의 전체 기능 동등성은 최종 목표로 유지한다. H01의 점검 완료를 전체 구현 완료로 해석하지 않는다. 수동 기능의 기반 결함 수정은 H03부터, 해당 기능을 AI 도구로 공개하는 작업은 검증 후 P05/P07에서 진행한다. 초기 계획의 P00 기준 검사는 H00~H02로 확대했다.

공무원 업무 표본은 H00부터 모든 단계의 검수에 사용한다. 기존 22번 설계의 임베딩/reranker는 검색 평가 후 선택하며 첫 loop의 선행 조건으로 만들지 않는다. P02는 사용자가 확정한 브라우저 인증이고 외부 CLI/MCP는 필수 조건이 아니다.

## 첫 실행 과제

[25번 문서의 첫 실제 점검](25-hangul-parity-and-state-plan.md)을 따른다. **Agent를 사용하지 않는 기본 편집 흐름과 상태 저장부터 한글과 비교한다.**

1. 실제 한글 빌드·환경·표본을 고정하고 메뉴/동작/기본값 기준을 기록한다.
2. 두 문서에서 직접 입력·선택·서식·표·쪽·보기·단축키·저장/취소를 재현한다.
3. 문서별 값과 새 문서 기본값을 구분해 탭 전환·파일 재열기·프로그램 재시작을 검사한다.
4. 차이와 상태 복원 결과를 보고한 뒤 기반 수정에 착수한다.
5. 기반 검증 후 같은 문서의 AI 수정·undo·저장 통합 회귀를 수행한다.

이번 변경은 계획 문서 갱신이다. 한글 전수 검사·상태 저장 구현을 완료했다고 표시하지 않는다. 각 실제 작업은 코드·검수 증거·남은 차이를 별도로 기록한다.
