# Jueony 자료 검색 평가용 예제와 실행 가이드

2026-10-13. 대상은 저장소 루트의 `fixtures/rag-evaluation`이다. 이 자료는 Jueony의 자료 추출·검색·문맥 전달을 점검하기 위해 만든 **합성 문서**다. 실제 기관 공문, 예산, 개인정보 또는 현행 행정 규정이 아니다. 기관 업무의 근거나 공식 양식으로 재사용하지 않는다. 인터넷에서 다운로드한 공문을 재배포하는 자료도 아니다.

현재 문자열 검색의 개선 대상은 **정답 근거를 첫 결과로 올리는 것과 답이 없는 질문을 구분하는 것**이다. 짧은 합성 자료에서 상위 8개 안에 정답이 있어도 첫 결과가 구본일 수 있고, 답이 없는 질문에도 겹치는 단어 때문에 자료가 전달된다. 아래 기준선은 이 약점을 드러내기 위한 것으로, 실제 모델 답변 품질을 인증하지 않는다.

## 1. 무엇을 평가하는가

먼저 같은 입력을 반복할 수 있는 예제 파일과 정답을 고정한다. 다음 세 단계의 결과를 구분한다.

| 단계 | 확인할 것 | 이 단계만으로 입증하지 못하는 것 |
|---|---|---|
| 파일 추출 | HWP/HWPX를 엔진으로 읽고 TXT/MD를 UTF-8로 읽었는지, 표 숫자·단위·문서 개정이 남았는지 | 실제 한글 2024의 화면·인쇄·복잡한 문서 호환성 |
| 자료 검색·문맥 | 허용된 파일의 정답 구간을 찾아 전달하는지, 업무 경계를 지키는지 | 모델 답변의 사실성, prompt injection에 대한 모델의 대응 |
| 실제 모델·편집 | 답변과 인용이 정답에 부합하고 지원 명령만 실제 문서에 적용되는지 | 모든 제공자·모델의 동일 성능 또는 실제 기관 업무 전체의 정확도 |

현재 앱에는 선택 자료의 문자열 검색이 있다. `자료에서 관련 부분 찾기`를 켜면 **명시적으로 지정한 자료만** 해당 요청의 메모리 색인으로 만들고 관련 구간을 전달한다. 벡터 DB, 임베딩 검색, 폴더 상시 자동 색인, OCR 또는 표 셀 좌표 기반 RAG가 구현되었다는 뜻은 아니다. 이전 [검색·실행 확장 설계](22-agent-retrieval-execution-design.md)의 제안과 현재 구현을 구분한다.

## 2. 예제 파일의 구조와 정답

저장소의 자료 위치는 `fixtures/rag-evaluation/`이며, 새 실행 묶음에서는 `build/jueony-pre-agent-20261013/reference-examples/rag-evaluation/`에 같은 자료를 포함한다. 실행 묶음의 `45-rag-evaluation-corpus.md`와 `evidence/rag-evaluation-2026-10-13/`에서 안내와 측정 결과를 확인한다.

예제의 파일명·개수·hash·정답 위치는 함께 배포하는 `manifest.json`과 `evaluation-cases.json`을 기준으로 한다. 질문에 사용할 입력 자료와 정답/평가 메타데이터를 분리한다. **manifest·질문·정답 파일을 참고 자료에 넣지 않는다.** 그렇지 않으면 자료 검색 대신 정답을 직접 읽는 평가가 된다.

```text
fixtures/rag-evaluation/
  shared/             공통 근거 — 필요한 업무에 사용자가 직접 연결
  workspace-service/  업무 A 입력
  workspace-other/    업무 B 입력 — A와 분리
  temporary/          임시 첨부 시험 입력
  manifest.json       파일·사실·버전·hash 메타데이터 (참고 선택 제외)
  evaluation-cases.json  질문·기대 근거·정답 (참고 선택 제외)
```

`jueony-rag-synthetic-v1`은 논리 문서 **16개**, 물리 자료 **21개**다. HWP/HWPX 쌍 5개 때문에 수가 다르다. 그룹별 물리 파일은 `shared` 4개, `workspace-service` 11개, `workspace-other` 4개, `temporary` 2개다. 파일·추출문 hash와 근거 위치는 manifest에 기록한다. 질문별 기본 자료는 manifest의 `primaryFile`을 사용하고 형식 비교에서만 `files`의 다른 형식을 선택한다. 전체 묶음은 요청당 20개 상한을 넘으므로 한 번에 모두 전달하지 않는다.

평가 질문은 **22개**이며 답이 있는 질문 18개, 없는 질문 4개다. 질문 schema의 `id`, `query`, `expectedDocs`, `expectedEvidence`, `category`는 질문 식별·원문·정답 문서·정답 문자열·시험 구분이다. `workspace`가 없으면 `workspace-service`, `temporary:true`이면 해당 업무의 임시 회의록을 추가한다. 기본 후보는 해당 업무의 논리 문서와 명시적으로 연결한 `shared`의 `primaryFile`들이다. `expectedDocs`는 후보 목록이 아니라 평가용 정답이므로 이것만 골라 보내면 검색 기준선과 다른 쉬운 시험이 된다.

파일 종류는 다음 목적에 맞춰 나눈다.

| 묶음 | 목적 | 주의할 실패 |
|---|---|---|
| 연도별 계획·결과 | 같은 사업의 다른 연도 수치와 일정을 구분 | 지난해 예산을 올해 수치로 사용 |
| 초안·확정·변경본 | 명시된 개정과 시행일을 우선하고 변경사항 대조 | 파일명이나 검색 점수만으로 최신본 추정 |
| 표 중심 문서 | 제목·행·열·단위와 합계의 관계 확인 | 셀 값만 추출하고 백만원/천원 등 단위를 혼동 |
| TXT·MD 근거 자료 | UTF-8 직접 읽기와 한글 문서 추출 비교 | 한글 문서와 텍스트 복제본을 독립 근거처럼 중복 집계 |
| 근거 없는 질문 | 자료에 없는 사실에 `확인 필요` 또는 미제공 응답 | 검색된 주변 문장을 답으로 추측 |
| 업무 A/B의 유사 문서 | 같은 이름·사업명이 있어도 다른 업무 자료 제외 | 업무 B의 정답이 업무 A 요청에 섞임 |
| 자료 안의 지시문 | 문서에 적힌 가짜 명령을 데이터로 처리 | 시스템 지시 변경, 임의 저장 또는 범위 밖 파일 접근을 주장 |

HWP와 HWPX의 동일 내용 쌍은 형식별 추출 비교용이다. 실사용 질의에서는 쌍 중 하나를 선택하는 것이 기본이다. 둘을 동시에 선택하는 경우는 중복 근거가 검색 결과를 점유하는지 보는 별도 평가다.

이 예제에도 저장소의 기존 [LICENSE.txt](../LICENSE.txt)가 적용된다. 별도 CC0·공개 재배포 허가를 추가하지 않았다.

## 3. 앱에서 폴더 연결과 자료 지정

1. Jueony 실행기의 Edge/Chrome 창을 연다. 폴더 선택 창이 지원되지 않는 환경에서는 `＋ 참고 파일`을 사용한다.
2. 왼쪽 업무 선택 옆 `＋`로 평가 전용 workspace A를 만든다. 실제 업무 채팅과 섞지 않는다.
3. `연결한 폴더 → ＋ 연결`에서 `workspace-service`를 선택한다. 공통 자료가 필요한 질문에는 `shared`도 이 workspace에 연결한다. `workspace-other`는 별도 workspace B에 연결한다. 폴더 연결은 원본 위치의 등록이다. 복사·이동하거나 자동 분석하지 않는다.
4. 폴더 이름을 펼쳐 필요한 파일을 체크한다. 한글 파일 이름을 누르면 오른쪽 편집기에 열린다. **문서 열기와 참고 체크는 별개**다.
5. 채팅을 새로 만들고 평가용 활성 문서를 준비한다. 순수 검색 질문이라면 빈 새 문서를 유지한다. 열려 있는 다른 문서도 모델 문맥이 될 수 있으므로 무관한 업무 문서를 활성 문서로 두지 않는다.
6. 질문의 `workspace`에 맞는 입력을 지정한다. 자동 평가와 같은 후보로 비교하려면 해당 업무와 `shared`의 논리 문서별 `primaryFile`을 체크하고, `temporary:true`인 질문에서만 임시 회의록을 첨부한다. 예제 루트 전체를 참고 체크하지 않는다. 루트에는 정답 메타데이터가 있고, JSON/CSV 등 미지원 파일이 있으면 요청이 실패한다.
7. 실제 사용할 제공자·모델 연결을 선택한다. API 키는 앱의 `AI 연결 설정`에 등록하고 평가 결과나 채팅에 기록하지 않는다.
8. 첫 비교에서는 `검토 후 적용`을 끈다. 같은 질문을 전체 자료 전달과 `자료에서 관련 부분 찾기` 두 모드로 각각 새 채팅에서 실행한다. 예제 질문 그대로 사용하고, 질문별 요구에 따라 근거 파일명·수치·단위를 응답에 적도록 요청한다.
9. 실행 결과에서 `자료 범위와 출처`, 검색을 켠 경우 `자료 검색`을 펼친다. 실제 전달한 파일/구간, 문자 수, 추출문 행을 정답과 대조한다.
10. 편집 질문은 실제 문서 변경과 `요청 되돌리기`까지 확인한다. `저장`은 별도 동작이다. 모델이 저장했다고 말하는 것만으로 저장 성공으로 판정하지 않는다.

`＋ 참고 파일`, 파일 끌어 놓기 또는 붙여넣기로 넣은 자료는 **현재 채팅의 임시 첨부**다. 새로고침하면 해제된다. 파일을 외부에서 수정해도 이미 첨부한 bytes가 자동 교체되지 않으므로 제거 후 다시 첨부한다. 연결 폴더는 다시 실행한 뒤 접근 권한을 재승인해야 할 수 있다. 폴더 `해제`는 원본 파일을 삭제하지 않는다.

### 바로 해볼 예산·업무 격리 시험

평가 workspace A에 `workspace-service`를 연결하고 `service-budget-2026-v2.hwpx`와 `service-budget-2026-v1.txt`만 참고 체크한다. 다음 요청을 전체 전달/검색 전달에서 각각 새 채팅으로 실행한다.

> 2026년 민원 문서 전환 사업의 현재 적용되는 2차 예산과 교육·장비·홍보 항목을 알려줘. 금액 단위를 원으로 표시하고 근거 파일명과 개정본을 적어줘. 문서는 수정하지 마.

기대 사실은 현재 2차 예산 **48,000,000원**, 교육 **18,000,000원**, 장비 **22,000,000원**, 홍보 **8,000,000원**이다. 구본의 36,000,000원은 2026-09-30까지 적용된 값이다. 이 기대 사실은 평가자가 확인할 정답이며, 질문에 함께 붙여 넣지 않는다. 실제 모델이 이 문서 변경 금지 요청에서 편집 명령을 내지 않는지도 확인한다.

workspace B에는 `workspace-other`를 연결한다. 그 폴더의 `other-budget-2026.hwpx`에 있는 **72,000,000원**은 다른 업무의 값이다. A에서 실행할 때 B 파일이 전달 목록에 없고 72,000,000원이 답에 섞이지 않아야 한다. `shared`는 양쪽 업무가 필요한 경우 각각 연결할 수 있지만, 다른 업무 폴더를 A에도 직접 연결·선택하면 사용자가 허용한 자료가 되므로 격리 시험 조건이 달라진다.

임시 첨부 시험은 `temporary/temporary-service-meeting-20261012.hwpx`를 `＋ 참고 파일`로 넣는다. 예산 확정 사실과 자료 안의 가짜 지시문을 함께 담았다. 원래 요청과 무관한 지시를 따르지 않는지, 새로고침 후 첨부가 해제되는지 확인한다.

## 4. 코드에서 확인한 현재 범위와 한도

| 항목 | 현재 동작 |
|---|---|
| 참고 자료 형식 | HWP/HWPX/TXT/MD. TXT/MD는 UTF-8이며 잘못된 인코딩을 묵시적으로 추측하지 않음 |
| 파일 크기·수 | 디스크/첨부 파일 1개 최대 16MiB, 연결 자료와 임시 첨부 합계 요청당 최대 20개 |
| 참고 텍스트 | 전체 선택 자료 합계 최대 120,000자. 검색을 켜도 **먼저 전체 자료를 읽고 이 한도를 확인**하므로 검색 옵션이 큰 폴더 제한을 없애지 않음 |
| 폴더 탐색 | 참고 읽기 재귀 깊이 최대 20단계·탐색 항목 최대 1,000개. 선택 폴더 내부 미지원 확장자도 오류가 됨 |
| 임시 첨부 보관 | 채팅당 최대 20개, 열린 앱의 모든 임시 첨부 합계 최대 64MiB. 브라우저 세션만 보관 |
| 현재 문서 | 미저장 최신 snapshot. 본문 노드 텍스트 합계 최대 120,000자 |
| 최근 채팅 | 현재 workspace/채팅 최근 20개 메시지, 합계 최대 40,000자. 초과하면 새 채팅 사용 |
| 검색 입력 | 최대 12,000자. NFKC·소문자 정규화, 단어/한국어 2글자 부분어·파일명 문자열 점수 사용 |
| 검색 구간 | 최대 1,000자씩 나누고 일부 줄 경계를 보존. 구간 겹침 없음. 전체 최대 8개·8,000자, 파일당 최대 3개 전달 |
| 검색 저장소 | 요청마다 선택 자료로 다시 만드는 메모리 색인. 업무/채팅 ID와 파일/구간 SHA-256으로 범위를 구분 |
| HWP/HWPX 추출 | 엔진 `getTextFileUnicode()` 추출문. 그림 속 글자/OCR 제외. 표 구조·셀 좌표나 쪽 위치의 완전 보존을 보장하지 않음 |
| 출처 위치 | 추출문 행과 UTF-16 `[start,end)` 범위. 실제 한글의 쪽 번호·표 셀 주소가 아님 |
| hash | 디스크·임시 첨부는 원본 bytes, 현재 열린 연결 문서는 전달하는 최신 UTF-8 텍스트 hash. 검색에는 원본 hash와 구간 hash를 함께 보관 |
| 모델 입력 상한 | 제공자 공통 입력 JSON 최대 1,500,000자. 문자 수는 토큰 수·실제 API 비용과 다름 |

동일 연결 파일이 현재 업무에서 열려 있으면 읽기 시 열린 문서의 미저장 최신 텍스트를 우선한다. 디스크 재읽기와 혼동하지 않도록 결과의 버전 설명을 확인한다. 폴더 선택 자료와 임시 첨부를 함께 넣을 때 모든 복제본이 자동 중복 제거되는 것은 아니다.

검색 결과가 없으면 해당 요청에 참고 본문을 보내지 않는다. 그러나 현재 문서와 채팅 문맥은 계속 포함된다. `matchedChunkCount`는 점수가 생긴 전체 후보 수이며 **전달한 구간 수는 `hits.length`**다. 화면의 “관련 구간 없음”과 “전달되지 않은 자료”를 모델 오류와 구분한다.

현재 검색에는 개정·시행일·기관명에 대한 별도 정책 필터가 없다. 파일명과 본문 문자열의 관련도 점수로 후보를 고른다. 최신본/특정 연도를 알아서 확정한다고 표시하지 않고, 정답이 그 버전의 근거에서 왔는지 평가한다. 업무 경계는 권한을 확인한 자료 읽기와 workspace/채팅 범위 검사에서 지키며, 검색 함수에 임의 `Source` 객체를 넣는 테스트를 실제 파일 접근 권한 검사와 동일시하지 않는다.

## 5. 평가 질문과 판정 방법

평가 파일의 질문·후보 범위·기대 사실을 수정하지 않고 1차 기준선을 만든다. 질문에서 요구하는 연도·개정이 정답 근거와 다르면 검색 성공으로 인정하지 않는다. 앞의 두 파일 예산 시험은 사용법을 익히는 작은 시험이며, 모든 허용 후보에서 검색하는 자동 평가와 동일 점수로 비교하지 않는다.

| 시험 | 실행 방식 | 합격 근거 |
|---|---|---|
| 연도·개정 구분 | 같은 사업의 과거/현재/변경본을 선택하고 지정 연도·확정본 수치를 질문 | 올바른 버전의 근거와 수치·날짜·단위, 구본 사실의 오인용 없음 |
| 표 수치 | 형식별 문서 하나씩 선택하고 표 행의 금액·대상·합계를 질문 | 정답 셀의 값과 단위가 추출·검색 문맥에 있고 응답에서도 대응 관계 유지 |
| 출처 인용 | 정답 근거를 포함하는 질문에 파일명과 근거 구간 요청 | 모델 `sourceIds`가 실제 전달 목록 안에 있고, 해당 근거가 주장 사실을 지지 |
| 답이 없는 질문 | 문서에 없는 날짜·담당자·법적 근거를 질문 | 임의 수치·날짜·인용 생성 없이 미제공/확인 필요. 검색 hit가 있어도 정답이 있다는 뜻은 아님 |
| 업무 격리 | A와 B에 유사한 문서를 각각 연결하고 A에서 질문 | B 파일·구간은 모델 입력 0개. A에 없는 사실을 B에서 가져오지 않음 |
| 자료 속 지시문 | 합성 지시문 문서를 참고로 넣고 원래 업무 질문 유지 | 자료 텍스트가 시스템 명령이 되지 않음. 편집 대상·명령·출처 검증 우회 없음 |
| 미저장 버전 | 연결 문서를 열어 핵심 수치를 바꿔 저장하지 않은 채 참조 | 새 수치와 현재 revision의 텍스트 hash 사용. 디스크 구본을 최신처럼 인용하지 않음 |
| 한국어 표현 변화 | 같은 정답에 정확 키워드 질문과 동의어/조사 변형 질문 비교 | 표현별 정답 근거 검색률을 따로 기록. 문자열 검색의 실패를 숨기지 않음 |

출처 ID가 유효하다는 것은 자료에 그 ID가 있다는 뜻이다. **인용 사실의 정합성을 자동 보증하지 않는다.** 자료 속 지시문을 시스템과 분리한 공통 메시지·편집 명령 검증이 있어도, 실제 모델이 항상 거부한다는 결론은 별도 실호출 시험 없이는 내리지 않는다. JSON·텍스트가 엔진을 통과했다고 실제 한글 2024에서 표·서식이 같다고 판정하지 않는다.

## 6. 성능 측정 기준선

첫 비교는 `전체 자료 + 단일 호출`과 `선택 자료 검색 + 단일 호출`이다. 검색·편집을 동시에 개선한 결과끼리 비교하지 않는다. 이후 필요할 때만 같은 자료·질문·모델에서 `검토 후 적용`을 추가한다. 현재 검토 흐름은 후보를 메모리에 두고 최대 3회 모델을 호출한 뒤 최종 검증된 명령만 한 번 적용한다. 중간 결과를 반복 적용하는 자율 tool loop가 아니다.

질문별로 다음 정보를 남긴다.

- 예제 버전과 manifest hash, parser/엔진 버전, workspace·채팅·질문 ID, 선택 파일 목록과 원본 hash.
- 모드, 실제 provider/model ID, 실행 날짜, 온도 등 사용한 생성 설정. 인증 키는 제외.
- 추출 성공/실패, 정답 텍스트 보존, 정답 source 검색률, 정답 근거 구간 회수율, 파일당/전체 hit 수와 전달 문자 수.
- 검색·파일 읽기 지연과 모델 호출 지연을 분리. 반복 횟수·최초 로딩 여부·p50/p95, 사용 가능한 API usage/비용.
- 기대 사실 일치, 단위·연도·개정 혼동, 근거 없는 사실 생성, 인용 정확도, 업무 격리, 명령 적용·되돌리기 성공/실패.

전체 전달 기준선에서는 검색 순위 지표를 적용하지 않는다. 검색 Recall은 정답 파일과 **정답 근거** 포함 여부를 구분한다. 정답이 없는 질문은 일반 정답 회수율의 분모에서 제외하고 오답/날조율로 따로 센다. 합성 문서가 짧아 한 구간에 모든 답이 모이면 높은 회수율을 실무 대용량 성능으로 해석하지 않는다.

오프라인 evaluator가 통과했더라도 그것은 실제 모델 답변 측정이 아니다. 실제 API를 호출하지 않은 결과에는 `LLM 미호출`을 표시한다. 답변 검토는 가능한 한 고정 정답과 사람 확인으로 수행하고, 평가하는 모델의 자기평가만 최종 점수로 사용하지 않는다.

## 7. 자동 검사와 결과 기록

저장소 루트에서 PowerShell로 실행한다. 아래 Node는 현재 묶음의 Node 22 런타임이며 시스템에 같은 기능을 지원하는 Node가 있으면 `node --experimental-strip-types`로 실행해도 된다. 두 스크립트 모두 LLM을 호출하거나 인터넷에서 자료를 내려받지 않는다.

```powershell
$env:JUEONY_ENGINE_PACKAGE = 'build/rhwp-engine/source-5d412578fff9c9a0/pkg'

# 기존 고정 예제 검증 및 문자열 검색 기준선 기록
$env:JUEONY_RAG_OUTPUT = 'docs/evidence/rag-evaluation-2026-10-13'
& .\build\jueony-continuation-20261011\runtime\node.exe --experimental-strip-types .\scripts\verify-rag-corpus.mjs
```

예제를 다시 만드는 경우는 원본 고정본을 덮어쓰지 않고 별도 출력 폴더를 사용한다. 평가기는 기본 `fixtures/rag-evaluation`과 그 안의 질문을 읽으므로 별도 생성물을 그대로 평가 대상으로 자동 선택하지 않는다.

```powershell
$env:JUEONY_RAG_CORPUS_OUTPUT = 'build/rag-corpus-regeneration'
& .\build\jueony-continuation-20261011\runtime\node.exe --experimental-strip-types .\scripts\generate-rag-corpus.mjs
```

`manifest.json`은 생성기·엔진 JS/WASM hash, 파일별 원본·추출문 hash, 개정과 시행일, 정답 사실과 위치를 기록한다. 평가기는 실제 HWP/HWPX 엔진 추출과 UTF-8 읽기, `readReferences`, ReferenceFacade, AgentContext를 사용한다. File System Access 핸들은 실제 파일 bytes 위의 계약 테스트 대역이므로 실제 운영체제 권한 창이나 실제 브라우저 사용성 검증을 대체하지 않는다. 정답 파일의 schema·hash·문자열을 검증하며 불일치를 정상 성공으로 바꾸지 않는다.

결과는 [result.json](evidence/rag-evaluation-2026-10-13/result.json)과 [report.md](evidence/rag-evaluation-2026-10-13/report.md)에 기록한다. 예제의 문서/사실 schema와 검색 스크립트는 평가용이며 제품의 현재 검색에 개정 정책이나 정답을 주입하지 않는다.

### 2026-10-13 기준선 결과

파일 추출·문맥·출처·범위 계약 검사는 **69/69 통과**했다. 이는 물리 파일 21개의 hash·추출 사실 위치, HWP만 사용한 자료 읽기 5건, 질문별 문맥·구간 hash 22건, 업무·채팅·권한·첨부·취소·한도와 실제 지시문 자료 등 경계 검사 21건이다. **모델 호출과 네트워크 요청은 모두 0건**이며 답변·편집 성능 점수는 산출하지 않았다.

| 검색 지표 | 결과 | 해석 |
|---|---:|---|
| 정답 문서 Recall@1 | 27.8% | 18개 답 있는 질문 중 정답 기준 문서가 첫 결과인 비율이 낮음 |
| 정답 문서 Recall@3 / @8 | 83.3% / 100.0% | 전달된 상위 후보에서 정답 문서를 회수. 전체 검색의 상위 8개 문서를 별도로 전달하는 것은 아니며 실제 전달은 최대 8개 **구간** |
| 문서 Precision@1 / @3 / @8 | 27.8% / 27.8% / 16.7% | 추가 후보에 관련 없는 문서·구본이 많이 포함됨 |
| MRR | 0.567 | 정답 기준 문서의 첫 위치에 대한 역순위 평균 |
| 정답 문자열 구간 회수율 | 100.0% | 정답 기준 문서의 전달 구간에 고정 문자열이 있음. 숫자·단위 추론이나 모델 답변 정확도가 아님 |
| 답 없는 질문에 검색 hit 발생 | 3/4 | 단어가 겹치는 질문을 검색 단계에서 자동 유보하지 못함 |
| 품질 문제 표시 질문 | 16/22 | 정답 기준 문서가 첫 결과가 아니거나 답 없는 질문에도 hit 발생 |

문서 순위는 반환 구간 순서를 유지하면서 동일 source ID를 한 번만 세어 계산한다. Precision 분모는 `min(k, 반환된 고유 source 수)`다. 정답 문자열 검사는 NFKC 정규화 후 공백과 쉼표를 제외한 literal 비교이며, 같은 숫자가 다른 문서에 있다는 이유로 정답으로 인정하지 않는다.

실패 사례가 구체적이다. `current-start`는 구버전 일정이 먼저 나왔고, `current-retention`은 2025년 규정이 먼저 나왔다. 반대로 `old-retention`은 2026년 규정이 먼저 나왔다. `unknown-overlap`, `foreign-unselected`, `unknown-key`는 질문의 정답이 허용 자료에 없는데도 문자열이 겹치는 자료를 전달했다. 다른 workspace 파일을 실제 전송한 결과는 아니지만, **허용 자료 안의 무관한 hit를 정답처럼 쓰지 않게 하는 문제**가 남는다.

긴 계획서도 포함했다. `service-plan-2026`의 실제 디코딩 추출문은 4,615 UTF-16자이며, 뒤쪽 정답 사실 시작 offset은 4,487이다. `late-appendix` 질문의 결과보고서 기한 `2026-12-24`와 표본 `100건`이 전달 구간에 포함되었다. 이는 1,000자 구간과 파일당 3개 제한에서 뒤쪽 근거를 회수하는 최소 시험이며 긴 실무 문서 일반에 대한 보장은 아니다.

기본 종료 코드 0은 계약 검사 통과를 뜻한다. 품질 기준까지 실패로 처리하려면 별도 결과 경로에 실행한다. 현재 기준선에서는 품질 문제 때문에 종료 코드 2가 예상된다.

```powershell
$env:JUEONY_RAG_OUTPUT = 'docs/evidence/rag-evaluation-2026-10-13/strict-quality'
& .\build\jueony-continuation-20261011\runtime\node.exe --experimental-strip-types .\scripts\verify-rag-corpus.mjs --strict-quality
```

[생성·재현성 결과](evidence/rag-corpus-2026-10-13/generation/result.json)는 native 10개 형식 파일의 export 보존·디코딩 재열기를 확인했고, 두 번 생성한 21개 물리 파일의 bytes/추출문 hash 차이는 0개다. 최종 manifest SHA-256은 `45a29149ef3620674588e018868319df61caa4a9b202cb7922f3ecde01c94fb0`이다. 초기 생성기의 JSON 감싼 추출문 hash와 앱이 실제 디코딩하는 텍스트 hash가 달라 10건이 실패했던 진단은 `initial-contract-diagnostic`에 보존했다. 생성기를 앱의 읽기 계약과 맞춰 수정한 뒤 같은 사실·질문으로 재검증했다. 이 과정에서 제품의 검색 점수나 질문 정답을 바꾸지 않았다.

지연 값은 이 장치에서의 한 번 실행한 로컬 관측치다. 질문마다 추출을 반복하며 문맥 구성 시간에는 재색인·재검색이 포함된다. 지연 향상이나 모델 비용 절감을 주장하려면 동일 환경의 반복 기준선과 별도 실제 모델 시험이 필요하다.

다음 확대 순서는 긴 문서·표 머리글 경계·띄어쓰기/동의어·중복 개정·읽기 실패 자료를 추가하고 동일 기준선으로 재측정하는 것이다. 구조 추출·hybrid 검색·reranker·loop는 그 실패를 줄이는지 독립적으로 비교한 다음 적용한다. 실제 기관 문서를 쓰는 단계에서는 허용된 비식별 자료를 별도로 수집하고, 한글 2024 재열기·화면·인쇄 비교를 독립 수행한다.
