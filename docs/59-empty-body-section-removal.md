# 빈 본문 구역의 명시적 삭제

2026-10-14. [54번 쪽 본문 지우기](54-complete-body-page-deletion.md) 이후 남은 빈 구역 정리를 추가한다. 한글 2024 직접 비교는 마지막 일괄 검수로 남긴다. 자동 경계 병합이나 한글 전체 쪽 지우기의 완료 판정은 아니다.

## 실제 동작과 범위

쪽 메뉴의 `빈 본문 구역 삭제`를 사용한다. 본문이 없는 문단 하나로 구성된 현재 구역을 용지·테두리·배경 설정과 함께 삭제한다. 뒤 구역이 있으면 그 구역의 처음으로, 마지막 구역이면 앞 구역 마지막 문단의 끝으로 커서를 옮긴다. 남은 구역은 서로 합치지 않으며 각각의 용지·기본 탭·글자/문단 서식·시작 번호·배경을 유지한다. 작업 하나의 undo/redo와 안전한 저장 경로를 사용한다.

기존 `쪽 본문 지우기 (완전 문단)`는 설정을 유지한 빈 문단을 남기는 동작을 유지한다. 그 뒤 필요할 때 새 명령으로 빈 구역을 정리한다. 공백 문자·줄바꿈·추가 문단은 자동으로 무시하지 않는다. 문서의 유일한 구역도 지우지 않는다.

전체 5,000문단·10만 문자 이내의 가로쓰기·한 단 일반 본문 문서부터 지원한다. 다른 구역을 포함하여 표·개체·필드·특수 영역·바탕쪽·줄 번호·숨긴 빈 줄·홀짝 시작·미지원 구역 기록이 있으면 차단한다. HWP3 계보 문서도 제외한다. 한 쪽으로 확인된 빈 구역만 대상으로 하며 본문이 없는 쪽 배경은 삭제할 구역의 설정이라고 안내한다.

## 모델·명령·계약

`zzzzzzzz-empty-section-remove.patch`는 `getEmptySectionRemovalPlan`과 `removeEmptySection`을 연결한다. 계획 조회는 변경 없는 검사이며 구역 수·쪽 수·이동할 커서와 토큰을 반환한다. 토큰은 삭제할 구역 번호, 문서 속성/서식과 모든 구역 모델을 결합한다. 단순 저장 캐럿 값은 정규화하여 내보내기 메타데이터 기록 때문에 오래된 문서로 오인하지 않도록 한다. 실제 UI 커서와 revision은 별도로 다시 검사한다.

삭제 후 전체 구역 수·쪽 수가 각각 하나 줄었는지와 남은 구역의 정의/문단 모델을 대조한다. 조판으로 갱신될 수 있는 측정 줄 기록만 비교에서 분리하며 본문·서식·제어·설정은 검사한다. 어긋나면 원문 모델을 복원한다. 구역 개수와 저장 캐럿을 실제 Document 모델에 기록하고 파생 조판 상태와 캐시를 갱신한다. 본문/서식 자원 풀을 임의로 정리하거나 기존 그림 바이트를 덮어쓰지 않는다.

문서 모듈의 `EmptySectionRemovalPlan`은 위치·토큰·개수·다음 커서의 계약이다. `adapters/rhwp/empty-section-removal.ts`가 실제 명령·저장 사본 preflight·live snapshot·undo/redo와 연결한다. 오래된 revision·대상·커서와 변경된 다른 구역은 거절하며, 적용 후 실패 시 문서·history를 복원한다. 범용 UI 명령 문자열을 Agent 편집 명령으로 열어 주지 않는다.

## 검증 기록

전용 엔진 검사는 첫·중간·마지막 빈 구역, HWP/HWPX 저장 재열기와 HWP의 실제 저장 캐럿, 남은 용지·서식·번호·이미지 자산, 쪽 본문 삭제 뒤의 정리, 반복 삭제, 공백/추가 문단·다른 구역의 표/다단/홀짝·오래된 토큰·다른 대상 토큰 거절을 대상으로 한다.

실제 Edge에서는 메뉴·예상 구역/쪽 수·커서 이동·undo/redo·취소·다른 구역의 변경·실문서 적용 후 실패 복원·좁은 화면·저장 재열기를 확인했다. 전용 실제 엔진 14개와 Edge 11개가 통과했다. 구역·본문·서식·배경·커서와 요청 단위 이력을 확인했으며 HWPX는 Jueony의 로컬 문서/커서 상태가 재실행 후 복원되는 것까지 별도로 검사했다. 최종 자동 회귀는 단위 411개, 브라우저 282개, 엔진 229개가 통과했다. TypeScript와 9개 모듈·229개 소스 경계도 통과했으며 실행 묶음 호환 4개를 포함한 보고서의 소스·통합 패치·WASM을 같은 빌드와 대조했다. [검증 요약](evidence/empty-section-2026-10-14/verification-summary.json)을 따른다. 한글 GUI/지면 동등성 검사는 아직 수행하지 않았다. Agent 회귀는 로컬 mock으로 수행하며 실제 유료 모델 호출로 계산하지 않는다.

## 발견한 저장 상태 제한

HWP는 삭제 후 캐럿이 실제 파일에 기록되고 새 엔진에서 같은 위치로 다시 열린다. HWPX는 엔진 파서가 settings.xml의 캐럿을 DocProperties로 읽지 않고, writer도 원본 settings.xml 또는 고정 템플릿을 유지하여 파일 자체의 캐럿이 복원되지 않는다. 이 경로를 통과한 것으로 계산하지 않는다. Jueony의 문서별 로컬 보기 상태·복구 checkpoint로 재실행 후 커서를 복원하는 기능과 구분한다.

[한컴의 HWPX 구조 설명](https://tech.hancom.com/hwpxformat/)은 settings.xml에 저장 시점의 캐럿이 들어감을 설명하고, [캐럿 요소 설명](https://tech.hancom.com/python-hwpx-parsing-1/)은 listIDRef·paraIDRef·pos를 제시한다. 본문/중첩 목록 ID 및 writer가 생성하는 문단 ID의 대응을 확인한 뒤 표준 캐럿을 읽고 갱신하는 후속 작업이 필요하다. 구역 번호를 문단 목록 ID라고 임의로 간주하거나 원본 PrintInfo/외부 설정을 덮어쓰지 않는다.

초기 통합 검사에서 리본에는 명령이 있었지만 원본 HTML 메뉴 catalog에는 빠져 있음을 발견하여 통합 쪽 메뉴에도 연결했다. 재실행 검사에서는 테스트용 직접 open/save만 호출하여 shell checkpoint가 이전 빈 문서로 남았던 문제를 실제 호스트 저장 버튼 경유로 바로잡았다. 제품의 복구/보존 검사를 완화하지 않았다.

엔진은 `build/rhwp-engine/source-0765146598abeac2/pkg`, WASM SHA-256은 `753d3d67ad49508df76485e1f3ebedfb84520965a1c599189a868dc3547d773a`이다. 앱 소스 SHA-256은 `a8eb730335f613d0db25d0ead8702eb4a76c3f83b8ad89a0270325db4668dba2`이다. 빌드는 직전 `3f7461d`와 작업 중 소스를 기록했으며 기능 커밋은 `a7bc791`이다. 보고서는 소스 바이트 해시로 최종 구현과 대조한다. 고정 업스트림은 변경하지 않았고 MIT/제삼자 고지를 유지한다.

새 실행 묶음은 `build/jueony-empty-section-20261014/Start-Review.cmd`, Rust 실행 파일은 같은 폴더의 `JueonyEditor.exe`, 주소는 `http://127.0.0.1:4238/`다. 한글로 열어볼 합성 결과는 `review-documents/empty-section/empty-native`와 `empty-browser`에 있다. 이전 실행 창·서버·사용자 문서를 유지하고 포트별 업무 저장소는 별도다.
