# HWPX 파일의 저장 시점 본문 커서

2026-10-14. [59번 빈 구역 삭제](59-empty-body-section-removal.md)에서 발견한 파일 캐럿 저장 누락을 보강한다. 문서별 로컬 보기 상태와 별도로, 지원하는 HWPX 파일 자체에 저장 직전 커서를 기록하고 새 엔진에서 다시 읽는다. 한글 2024 직접 비교는 마지막 일괄 검수에 남긴다.

## 지원 범위

단일 구역의 일반 본문 목록을 지원한다. 최대 5,000문단·10만 문자이며, 첫 문단의 구역/단 정의 외에 표·개체·머리말·꼬리말·각주·필드·차례 표지·영역 태그·탭·텍스트 제어문자가 없어야 한다. 첫 문단의 구역/단 정의도 각각 하나까지만 허용한다. 빈 문단, 문단 나누기로 만든 여러 문단, 한글과 이모지의 시작·중간·끝 위치를 포함한다. 바탕쪽과 HWP3 계보도 제외한다.

다중 구역·중첩 목록의 `listIDRef` 대응을 추측하지 않는다. 지원하지 않는 문서는 원본 settings.xml을 그대로 통과시키고 Jueony의 검증한 로컬 보기 상태를 계속 사용한다. 복잡한 문서 전체의 파일 커서 복원이 완료되었다고 계산하지 않는다. 기본 템플릿에 캐럿이 없는 경우를 새로 보충하거나 알 수 없는 XML 설정을 재작성하지 않는다.

## 모델과 저장 경계

`zzzzzzzzz-hwpx-body-caret.patch`의 `parser/hwpx/caret.rs`에서 읽기·지원 범위·UTF-16 경계·설정 갱신을 분리한다. 현재 문서 모델의 캐럿은 기존 `setCaretPosition`/`getCaretPosition` 계약을 사용한다. 편집 명령·undo/redo·저장 UI를 새로 만들지 않고 기존 저장 직전의 실제 UI 캐럿 기록 경로와 연결한다. 디스크 파일을 별도로 편집하지 않는다.

읽기에서는 공식 앱 namespace의 루트 바로 아래 CaretPosition 하나와 목록 0만 받는다. 숫자 범위와 실제 문단의 문자 경계를 검사하며 이모지의 UTF-16 중간 위치, 존재하지 않는 문단, 잘못된 목록, 중복 요소, 손상 XML은 복원하지 않는다. DTD도 처리하지 않는다. 2011/2023 앱 namespace와 다른 접두사를 지원하며 설정 입력에는 별도 1MiB 상한을 둔다.

저장 시에는 현재 모델의 유효한 본문 위치가 기준이다. 기존 목록 0의 숫자 위치가 문단 범위를 벗어나거나 문자 중간을 가리켰더라도, 사용자가 유효한 새 위치에서 저장하면 새 좌표로 갱신할 수 있다. 오래된 원본 좌표를 현재 문서에 대조해 저장을 막으면 문단 삭제 뒤에도 원래 커서가 남기 때문이다. 잘못된 namespace·목록·XML 구조에는 이 갱신을 적용하지 않는다.

settings.xml 전체를 재직렬화하지 않는다. CaretPosition의 시작 태그에 있는 세 숫자 속성만 갱신하고 나머지 설정의 바이트를 유지한다. 캐럿 태그의 미지 속성과 XML 엔티티도 보존한다. PrintInfo·외부 설정·주석·루트 namespace를 덮어쓰지 않는다. 일반 본문 writer가 내보내는 첫 문단의 구역/초기 단 정의 두 슬롯은 16 HWP 단위로, 이후 본문은 각 문자 UTF-16 폭으로 계산한다. 중복 구조 정의와 기타 제어 위치는 범위 밖으로 둔다.

## 근거와 독립 검사

[한컴 HWPX 설명](https://tech.hancom.com/hwpxformat/)은 settings.xml에 저장 시점 캐럿이 들어감을 설명한다. [캐럿 요소 설명](https://tech.hancom.com/python-hwpx-parsing-1/)은 listIDRef·paraIDRef·pos를 제시하고, [GetPos 계약](https://developer.hancom.com/en-us/webhwp/devguide/hwpctrl/methods/getpos)은 목록·문단·문자 위치를 구분한다. 이 설명만으로 다중 구역이나 중첩 목록 ID를 구역 번호와 동일시하지 않는다.

고정 업스트림 HWPX 표본에는 XML `p@id`가 0 또는 2147483648로 반복되지만 캐럿 문단 값은 서로 다른 파일이 있다. 따라서 XML 문단 ID를 직접 찾는 구현을 피하고 검증된 목록 0의 본문 순서를 사용한다. [표본 메타데이터](evidence/hwpx-caret-2026-10-14/caret-samples.json)에 파일 해시·캐럿·본문 문단 ID만 기록한다. 본문 내용은 복사하지 않는다. 이 조사와 엔진 왕복만으로 실제 한글의 모든 위치 의미가 확정되었다고 보지 않는다.

전용 실제 엔진 검사는 반복 XML 문단 ID, 두 namespace, 빈/첫/일반 문단의 모든 문자 경계, 3회 저장 왕복, 인쇄/외부 설정 보존, 잘못된 위치·목록·XML·중복 구조, 다중 구역/표 제외, 저장 시점 커서 우선, HWP 회귀를 확인한다. ZIP 내부 settings.xml은 별도 Python 검사로 대조한다. 초기 검사에서는 범위를 벗어난 기존 좌표와 유효한 새 저장 좌표를 모두 원본 보존으로 기대한 두 항목이 실패했다. 읽기 거절과 유효한 새 저장을 구분하도록 계약과 검사를 명시했으며, 설정 구조가 불명확한 경우의 보존 검사는 유지한다.

실제 Edge에서는 로컬 복구 기록 없는 파일 열기, 저장 직전 커서 우선, 편집 undo/redo, 빈 문단/첫 문단, 설정 보존, 외부 파일 변경 거절을 검사한다. 파일 충돌 경고는 테스트가 실제로 닫고 정확한 예상 오류 하나를 별도 기록한다. 다른 오류를 일괄 무시하지 않는다. 기존 사용자 창·문서·서버는 유지하고 합성 OPFS 파일과 별도 headless 프로필을 사용한다.

최종 검증 수와 빌드 해시는 [검증 요약](evidence/hwpx-caret-2026-10-14/verification-summary.json)을 따른다. 기존 모든 쪽 편집 회귀, TypeScript, 모듈 경계, 실행 묶음 호환을 같은 엔진으로 확인한다. Agent 회귀는 유료 모델 대신 로컬 mock을 사용한다. 한글 2024에서의 실제 파일 열기·커서·지면 비교는 아직 실행하지 않았다.

## 실행과 후속 과제

새 검수본은 `build/jueony-hwpx-caret-20261014/Start-Review.cmd`, Rust 실행 파일은 같은 폴더의 `JueonyEditor.exe`, 주소는 `http://127.0.0.1:4240/`이다. 한글에서 열어볼 합성 문서는 `review-documents/hwpx-caret/caret-native`와 `caret-browser`에 준비한다. 이전 실행 창과 origin별 업무 저장소는 유지한다.

다중 구역의 본문 목록, 표/글상자/머리말/각주 등 중첩 목록, 탭·필드·인라인 개체의 위치 대응, 복잡한 쪽 편집과 Agent 제어 확장이 남는다. 전체 문서화된 구현 범위는 완료되지 않았으며 자동 계속 작업을 유지한다. 고정 업스트림을 수정하지 않고 MIT/제삼자 고지를 유지한다.
