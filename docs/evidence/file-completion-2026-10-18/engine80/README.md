## 수정한 원인

- 모든 지원 HWP/HWPX 저장에 전체 쪽 수와 공개 control/text 응답 비교를 필수로 연결했다. 알려진 좌표만0.2 허용하고 그 밖의 필드·순서·ID는 정확히 비교한다. 읽기 실패·크기 한도·source handle 별칭·재열기 객체의 공유 DTO도 성공으로 처리하지 않는다.
- 캡션 생성/삭제에서 번호 할당과 조판 캐시를 즉시 갱신하고, 부분 속성으로 없는 캡션을 만들지 않는다.
- 표 전치 뒤 이전 행의 측정 높이를 새 행에서 재사용하지 않는다.
- 탭 payload가 미해결인 문단의 실제 간격 변경 시 기존 vpos 갱신 경계를 적용한다.
- 분할 정책 Cell/Row라도 실제로 통째로 들어간 이전 표의 물리 밴드가 입증되면 후속 표의 저장 원점이 그 내부로 되감기지 않는다. 중첩·분할 조각·불명확 소유는 기존 경로를 유지한다.
- 새 표 뒤에 앱이 만든 빈 이웃 문단의 줄을 원본 조판 증거처럼 표시하지 않는다.
- 새 도형의 배치 enum과 packed attr를 생성 시점부터 기존 동기화 함수로 일치시킨다.

[독립 Rust 후보·초기 실패](../engine78/candidates/README.md)와 합본 결과는 별도 근거다. 동결 후보를 합쳤다고 검수 통과로 간주하지 않고 이80으로 다시 실행했다.

## 남은 결함과 실패 이력

복합 HWPX의 HWP 변환2건은 미완료다. 실제 한글 사본은77/80에서 원래16쪽을 복구했지만 HWP 변환 시15쪽·22,186 지면 차이가 남는다. 과거 변환본은15쪽·125차이다. 76의15쪽·188차이와 다른 버전의 관측값이다. 저장 보호가 이 손상을 차단하는 성공을 무손실 변환 성공으로 세지 않는다.

새 문서의 굴림체 줄 수용30/31 차이와 실제 한글의 절대 조판 차이도 남아 있다. [실제 한글 줄 수용 증거](../line-fit76/README.md)를 유지한다. 이후 격리 실험의 미통과 후보를80에 넣지 않았다.

78의 표/새 구역 회귀 실패, 캡션3실패, 도형 raw 배치3→0 차이, 초기 Canvas 하니스에 요청이 없던 실패를 함께 보존했다. Windows 경계 화면 검수의 첫 실행은 잘못된 cwd로 시작 전에 연결 실패했다. 같은 검수기를 올바른 cwd·새 출력으로 다시 실행한8개 성공과 구별한다.
